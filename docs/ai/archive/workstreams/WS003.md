# WS003 - Workstream-first Context Control Layer

## 边界说明

本 Workstream 使用强隔离协作协议。AI 执行前应先运行 `acf workstream context WS003` 获取专属上下文入口；完成或切换状态前应运行 `acf workstream guard WS003` 检查实际改动是否越界。

- `read_scope` 是允许读取的默认上下文入口。
- `write_scope` 是允许直接修改的范围。
- Task Workstream 不直接修改 authority 文件；Maintenance / Merge Workstream 只有在 front matter 显式声明 `authority:` 范围时才能修改对应高权威文件。
- active workstream 默认禁止重叠写入；共享文件必须显式使用 `shared:` 并指定 merge_owner 或 serial coordination。

## 目标

完善 Workstream-first 上下文治理整体设计，使 ACF 能通过文档分层、可信 Knowledge、结构化链接图、低冲突 Workstream guard 和 Workstream-first 入口，让 agent 在项目内自然获得合适权威上下文，并持续治理重复、冲突、错误、过期和未升格内容。

本 Workstream 已从规划审查升级为 Maintenance 实施线：先形成五个模块规划，再在同一 WS 内落地已授权的 CLI、模板、README 和高权威文档改动。暂不自动推进 ReadyToMerge、Merging 或 Done；完成判断以标准验收集、全量测试和发布前检查为准。

## 设计共识

1. ACF 不追求最小上下文，而追求范围恰当、权威清楚、略宽但有理由的上下文。
2. 合适上下文主要来自项目文档信息架构和渐进式披露，不应主要依赖工具临时列文件清单。
3. `reference/` 是项目内中间材料层，可以包含规划、设计、背景、分析、手册和阶段性方案，不应全部视为高可信事实。
4. `Knowledge` 是从 reference、worklog、Workstream、ADR 或测试证据中精炼出的高可信可复用知识，门槛应高于普通 reference。
5. Workstream 是 agent 当前执行容器；Task_Plan 保留为单线或主线计划工具，但不再假设是 agent 日常工作的唯一中心。
6. Backlinks 是派生导航信息，只能由 ACF 从结构化关系生成，不允许 agent 手写反向链接正文。
7. Obsidian `[[双链]]` 只服务人工导航；ACF 继续使用普通 Markdown 链接、front matter、heading、table 和 generated marker 作为机器依据。
8. Workstream scope 是变更归属契约，不是整个工作区排他锁；guard 不应因为同一工作区存在其他 WS 的 dirty files 而默认失败。
9. Workstream-first when active 只表示当前执行入口优先，不表示 Workstream 替代 Context、Task_Plan、Current_Task、ADR、rules 或 Knowledge 的事实源职责。
10. 查询类命令必须保持只读；生成草案、sync、rewrite、promote、archive 等写入动作必须在命令名、参数和 JSON payload 中明确暴露 changed_files / planned_changes。

## 总体信息架构目标

### 分层模型

| 层级 | 主要位置 | 角色 | 默认读取策略 | 写入/升格边界 |
|---|---|---|---|---|
| Workstream 执行层 | WS 详情文件 | 当前执行线、阶段、scope、发现、证据、待合并结论 | 有 Active/Blocked/ReadyToMerge/Merging 时读取索引，再按 WS 读取详情 | 只能写自身详情和声明的草案/assigned 文件；不能直接污染 authority |
| Active 当前事实层 | `active/Context.md`, `active/Feedback_Inbox.md`, `active/Workstreams.md` | 当前阶段事实和入口 | 默认薄读 | 不放历史过程、完整方案、未审阅 WS 发现 |
| Reference 中间材料层 | `reference/*.md` | 背景、规划、设计、分析、手册、阶段性方案 | 按场景读取 | 可作为 Knowledge 来源，但不是全部高可信 |
| Knowledge 高可信精炼层 | `reference/Knowledge_Index.md`, `reference/knowledge/*.md` | 有证据和适用边界的可复用知识 | 按 tags/read_when 推荐读取；不全量默认读 | Draft 宽松；Active 严格；Promoted 指向更高权威 |
| Rules / ADR 权威约束层 | `rules/*.md`, `decisions/ADR-*.md` | 必须遵守的规则和稳定决策 | 按场景或 AGENTS 指引读取 | Knowledge 可 promote，但默认生成草案，显式 apply 才写 |
| Evidence 历史证据层 | `worklog/`, `archive/`, tests, reports | 追溯、证明、审计 | 默认不读；需要证据时读取 | 不作为当前事实；可支持 Knowledge evidence |

### 文档治理目标

1. 减少重复：同一结论只有一个权威位置，其他位置用链接或索引引用。
2. 暴露冲突：同一对象被多个 Knowledge / ADR / rule 指向时，可通过 link graph 和 backlinks 发现。
3. 发现错误：结构错误、断链、状态不一致、缺证据和过期审阅应能被 check/review 发现。
4. 控制污染：WS 发现、reference 草案和 worklog 过程不能直接变成 active 当前事实。
5. 支持 agent：所有 AI-facing 命令输出稳定 JSON、error_code、next_actions 和 changed_files。

### 横向实现边界

1. WS003 当前为 Maintenance Workstream，允许在 front matter `write_scope` 已声明范围内完成 Slice A-E 的代码、文档、测试和包清单变更。
2. 本文件中未声明的实现目标仍只是候选范围；真正落盘前必须先扩展 write_scope / merge_targets，并同步 Workstreams 索引。
3. 所有新增命令默认遵守 ACF JSON 契约：`schema_version`、`ok`、`command`、`context`、`error_code`、`warnings`、`next_actions`，写命令还必须包含 `changed_files`，只读命令必须返回 `changed_files: []`。
4. `check --strict` 只检查低误报结构问题、断链、状态机和机械门槛；不得裁决语义事实真假或证据是否“足够有说服力”。
5. minimal / legacy 项目必须保持低噪声：未启用 Workstream、没有 Knowledge v2、没有 backlinks marker 时，不应因为新能力产生 strict error。
6. 高权威文件写入一律显式化：rules、ADR、active 当前事实、manual、architecture 等目标默认只生成 draft / dry-run / planned payload，只有显式 `--apply`、明确目标和通过 scope/authority 检查后才能写。
7. authority path 第一版分类：
   - 当前事实 authority：`active/Context.md`、`active/Task_Plan.md`、`active/Current_Task.md`、rules、ADR、长期设计 reference。
   - 派生索引 / generated view：`active/Workstreams.md`、Knowledge / Decisions / Archive generated index block。
   - Task Workstream 永远不能直接写当前事实 authority；但可在显式 write_scope 中声明并写派生索引 / generated view，前提是该索引由详情或 marker 重算、且 scope 类型为 `assigned:` / `shared:` / 对应 sync 命令。
   - `active/Workstreams.md` 是 Workstream 详情派生索引，不等同 `active/Context.md` 当前事实 authority；guard 的 authority_write_attempts 不应把声明过的派生索引写入误判为当前事实污染。

## 模块 1：项目内信息架构与渐进式披露

### 目标

将 ACF 的默认上下文模型从 Task_Plan-first 调整为 Workstream-aware / Workstream-first when active，同时明确 reference、Knowledge、rules、ADR、worklog、archive 的职责边界，让 agent 通过文档结构自然获得合适上下文。

### 具体需求

1. 更新顶层设计和手册口径：
   - `active/Context.md` 是当前事实入口，不承载完整共享知识。
   - `reference/` 是中间材料层，不等同高可信 Knowledge。
   - `Knowledge` 是高可信精炼层，必须有来源、证据和适用边界。
   - 有 Active Workstream 时，Workstream 详情是当前执行上下文核心。
2. 更新 `AGENTS.md` 读取策略：
   - 当前有 Active/Blocked/ReadyToMerge/Merging Workstream 时，优先进入 Workstream 索引和对应 WS context。
   - `Task_Plan.md` 为 Empty 时不应成为默认注意力中心。
   - `reference/Knowledge_Index.md` 按场景读取，不默认全量读。
3. 定义 reference 文档状态和读取提示：
   - 可使用 section 级状态，如 `Draft / Active / Superseded`。
   - 不要求所有 reference 立刻 front matter 化。
4. 增加文档治理说明：
   - WS 发现进入 Knowledge / rules / ADR 前必须经过 draft/apply/promote 流程。
   - reference 可承载临时规划，但不能自动升格为事实。
5. 明确入口优先级和事实源优先级：
   - Workstream 详情是该 WS 的 metadata、scope、stage、merge request、当前发现和证据事实源；`active/Workstreams.md` 是派生索引，不覆盖详情。
   - `active/Context.md` 仍是项目当前事实入口；`Task_Plan.md` 仍是主线任务板事实源；ADR/rules 仍是稳定决策和规则事实源。
   - WS 发现需要升格时，只能通过 merge request、writeback draft、Knowledge draft/apply/promote 或显式维护命令进入 authority 层。
6. 定义 Workstream-aware 默认读取算法：

| 场景 | 默认入口 | 读取策略 | 风险处理 |
|---|---|---|---|
| 无 Active/Blocked/ReadyToMerge/Merging WS | `Task_Plan.md` / `Current_Task.md` | 保持现有单线流程 | 不因缺 Workstream 增加噪声 |
| 有且只有一个 Active WS | Workstreams 索引 -> `acf workstream context WSxxx` | 进入该 WS 详情；`Task_Plan` Empty 不代表无任务 | 保持 Context / ADR / rules 的事实源优先级 |
| 只有一个 Blocked WS | Workstreams 索引 -> `acf workstream next-actions WSxxx` | 优先展示 blocker 和解除阻塞路径；必要时读取 WS context | 不推荐 ready/done，不回落成“无任务” |
| 多个 Active-class WS | Workstreams 索引 / dashboard | 不默认读取所有详情；根据用户消息、Current_Task 当前执行线、owner 或显式 WS ID 选择 | 无法选择时返回候选并要求选择 |
| 只有 Done/Cancelled WS | 默认跳过 Workstreams 详情 | 仅在归档、审计或追溯时读取 | Done/Cancelled 不长期污染 active |
| Current_Task 与 WS 指向冲突 | 读取两者并报告冲突 | 不静默覆盖 | 生成 next_actions 指向人工/主 agent 判断 |
| 用户显式指定 WS | 指定 WS context | 用户当前消息优先 | 仍受 write_scope 和 authority 边界约束 |
| ReadyToMerge / Merging WS | workstream next-actions / merge context | 优先处理合并、返工或完成条件 | 不把 ReadyToMerge 当作已写入权威事实 |
7. 定义 reference 状态最小规范：
   - doc-level 可在文件顶部写 `Status: Draft / Active / Superseded` 或等价 heading；section-level 可写 `状态：Draft / Active / Superseded`。
   - `Superseded` 必须指向替代文件或 section；无法确定时只能作为 audit candidate，不进入 strict。
   - reference 内部可信度分层：System Manual、Top-Level Design、ADR 索引等仍是高价值设计资料；“中间层”只表示不是所有 reference 都自动等同高可信 Knowledge。
   - 第一版只在文档中说明状态格式；不强制所有 reference front matter 化，不让旧项目新增错误。

## 模块 2：Knowledge v2 高可信知识层

### 目标

在复用现有 Knowledge 结构的基础上升级为 v2：保留 `Knowledge_Index.md`、`reference/knowledge/KNNN-*.md`、`worklog/knowledge-drafts/`、draft/apply/mark/sync、状态机、相似去重和 generated marker；新增 metadata、证据门槛、读取触发和 Active 严格校验。

### 现有能力保留

1. `K001` 稳定 ID。
2. 索引 + 详情结构。
3. `knowledge draft -> apply -> mark -> sync` 生命周期。
4. `Draft / Active / Promoted / Stale / Rejected` 状态。
5. generated marker 只同步索引块。
6. `来源` Markdown 引用检查。
7. placeholder-like draft content strict 检查。
8. 相似 Knowledge 去重。
9. stale draft review。

### v2 metadata

新 Knowledge 详情建议使用 front matter：

```yaml
---
id: K001
status: Draft
tags:
  - workstream
source:
  - reference/Workstream_Design.md
evidence:
  - tests/test_cli.py
validated_by:
  - dogfooding
applies_to:
  - 多 agent 并行 Workstream 开发
not_applies_to:
  - 单文件短修复
read_when:
  - 当前任务由 Workstream 承载
  - 多个 agent 同时执行多个 WS
last_reviewed: 2026-06-09 12:00 +08:00
stale_after_days: 60
promoted_to: []
supersedes: []
depends_on: []
derived_from: []
related: []
---
```

正文结构：

```markdown
## 结论

## 适用场景

## 不适用场景

## 证据

uv run python -m unittest tests.ws003_acceptance; uv run python -m unittest; uv run acf check docs/ai --strict --json; uv run acf check template; minimal_smoke; upgrade_matrix; workstream guard --files

## 来源

## 使用建议

## 与现有事实源的关系

## 去重判断
```

### v2 schema 与兼容约束

1. 旧 Knowledge 无 front matter 时继续按现有 section 格式解析和检查，不因缺 v2 metadata 报错。
2. 新 draft 默认生成 v2 front matter；一旦文件存在 front matter，则按 Knowledge v2 schema 校验。
3. `source`、`evidence`、`promoted_to`、`supersedes`、`depends_on`、`derived_from`、`related` 使用普通规范化路径字符串或空列表，不使用 Markdown link 或 Obsidian `[[双链]]`。
4. 路径解析顺序：context root、当前 Knowledge 文件目录、project root；输出 JSON 必须标记 resolved_path、scope 和 missing reason。
5. Active / Promoted 下 `source`、`evidence`、`promoted_to` 等结构化路径断链在 `acf check --strict` 和状态门槛中是 error；`links check` 可先报告 warning + severity，由 Knowledge 状态校验决定是否升级为 error。
6. Draft 下缺失或断链默认 warning / skipped item，不进入 strict 失败，但必须在 JSON warnings / skipped_items 中可见。
7. v2 正文保留 `## 来源` section，draft renderer 同时写 front matter `source` 和正文 Markdown 引用；后续 parser 可 metadata 优先，但不得让现有来源检查失效。
8. `stale_after_days` 需要先扩展当前 strict front matter parser 和 schema，使该字段可作为正整数 scalar；不引入完整 YAML 解析器，也不放开任意数字字段。
9. `last_reviewed` 第一版接受 `YYYY-MM-DD` 或 `YYYY-MM-DD HH:MM +08:00`；stale 计算按日期部分 + `stale_after_days`，无时区时按本地日期处理，解析失败在 Active / Promoted 下为 error。
10. `KnowledgeFrontMatterSchema` 必须显式定义 allowed_fields、required_fields、scalar/list/integer/enum 字段和状态差异门槛。
11. v2 allowed_fields 第一版为：`id`、`status`、`tags`、`source`、`evidence`、`validated_by`、`applies_to`、`not_applies_to`、`read_when`、`last_reviewed`、`stale_after_days`、`promoted_to`、`supersedes`、`depends_on`、`derived_from`、`related`。
12. Draft 阶段 `id` 可以是 `K-DRAFT` 或空缺；`knowledge apply` 分配下一个 `KNNN` 后必须重写 front matter `id` 和标题中的 ID。若 draft 已含真实 `KNNN`，apply 必须检查冲突：冲突则拒绝，无冲突也以分配结果为准并在 warnings 中说明重写。
13. metadata 文本值允许中文；机器匹配只依赖字段名、状态枚举、路径和日期，不依赖自然语言事实裁决。

### 状态门槛

| 状态 | 语义 | 检查策略 |
|---|---|---|
| Draft | 候选知识，已进入 Knowledge 系统但未验证完成 | 允许缺部分字段，但必须标记 Draft |
| Active | 高可信可复用知识 | 必须有 source、evidence、applies_to、not_applies_to、last_reviewed、结论和证据 section |
| Promoted | 已升级为 rules/ADR/manual/architecture 等更高权威位置 | 必须有 promoted_to；agent 优先读取 promoted_to |
| Stale | 可能过时 | 不推荐默认读取，保留历史 |
| Rejected | 提炼错误或不适用 | 默认不读 |

Active / Promoted 门槛：

1. Active 必须有非空 `source`、`evidence`、`applies_to`、`not_applies_to`、`last_reviewed`，并有 `## 结论`、`## 证据`、`## 来源`。
2. Promoted 必须有非空 `promoted_to`，并且 agent 读取时优先提示 promoted target，而不是继续把 Knowledge 当最高权威。
3. v1 legacy Active 在无 front matter 时继续按旧 section 规则通过；只有用户显式迁移、v2 draft apply 或新增 front matter 后才执行 v2 严格门槛。
4. `mark --status Active` 只允许把符合 v2 门槛的 v2 Knowledge 标为 Active；旧 Knowledge 若需保持 Active，可保留旧格式，不被自动重写。

### 命令需求

1. `acf knowledge draft`：
   - 默认生成 v2 front matter。
   - 支持 `--from-workstream WS003`。
   - 支持 `--evidence`、`--applies-to`、`--not-applies-to`、`--read-when`。
2. `acf knowledge apply`：
   - 把草案进入 `reference/knowledge/`，默认仍为 Draft。
   - apply 后必须更新或同步 `Knowledge_Index.md`；实现可继续沿用当前 apply 即时更新索引，或统一调用 `knowledge sync` 的 generated renderer，但行为必须在 JSON 中暴露 changed_files。
   - 不允许直接 apply 为 Active，除非显式参数后置设计。
3. `acf knowledge mark --status Active`：
   - 触发高可信结构门槛。
   - 缺 evidence / applies_to / not_applies_to / last_reviewed / 来源 section 时拒绝，并返回稳定 error_code。
4. `acf knowledge promote`：
   - 默认生成 writeback draft，不直接写 rules/ADR/reference。
   - 默认草案路径进入 `worklog/writeback-drafts/`，文件名包含 Knowledge ID 和 promote 目标类型。
   - 草案最小结构包含 source Knowledge、目标文件、拟写入 section、理由、证据、风险和建议命令。
   - JSON payload 必须包含 `draft_path`、`planned_target`、`planned_changes`、`changed_files`、`warnings` 和 `next_actions`。
   - 显式 `--apply` 才写目标文件；`--apply` 必须指定 target type 和 target path。
   - 允许目标白名单第一版限定为 `rules/*.md`、`decisions/ADR-*.md`、`reference/*.md`、`template/reference/*.md` 中明确声明的目标；`active/Context.md` 默认拒绝。
   - `--apply` 必须支持 `--dry-run --json --check-after`，并在 Workstream 中受 authority / merge request / scope 规则约束。
   - Task Workstream 中的 promote apply 不得越过 merge request 直接写 authority。
5. `acf knowledge sync`：
   - 从 v2 metadata 优先生成索引。
   - 兼容旧 section 格式。
   - 第一版不扩宽主索引表；若需要推荐读取，先在 JSON payload 输出 `read_when_summary` / `applies_to_summary`，后续再评估表格列。
6. `acf review stale`：
   - Active Knowledge 使用 `last_reviewed + stale_after_days`。
   - 旧 Knowledge fallback 到文件日期或现有 Draft 逻辑。
   - `--days` 作为无 `stale_after_days` 时的 fallback；Promoted 默认提示读取 promoted target；Stale / Rejected 不推荐默认读取。
7. Knowledge 推荐读取：
   - `workstream context` 只推荐 Active Knowledge，Promoted Knowledge 只返回 promoted target 提示。
   - `read_when` 第一版使用大小写不敏感的关键词包含匹配，不做向量检索或语义裁决。
   - 匹配语料只使用用户当前请求摘要、Workstream title、Mission、current_stage 标题、read_scope 路径、write_scope 路径和 Knowledge tags；不扫描完整 WS 正文、worklog、archive 或 draft 正文。
   - JSON 输出必须包含 matched_terms、matched_fields、knowledge_id、status、reason 和 promoted_to。

### 实现路径

1. 先在 parser 层扩展 strict front matter helper，支持 schema 允许的正整数 scalar；不新增依赖，不支持任意 YAML。
2. 新增 Knowledge schema 和 metadata extraction helper，并保留旧 section fallback。
3. 更新 draft renderer。
4. 更新 apply 逻辑，分配 KNNN 后重写 v2 front matter id，并检测 draft 内真实 KNNN 冲突。
5. 更新 sync 行生成逻辑，兼容旧格式。
6. 更新 mark Active 校验。
7. 更新 check strict：
   - Draft 宽松。
   - Active/Promoted 严格。
   - strict 只检查机械字段、日期、断链和 section 存在，不裁决知识内容真假。
   - source/evidence severity 必须状态感知：Draft warning，Active/Promoted error。
8. 增加 fixture：
   - v1 legacy Knowledge 仍通过。
   - v2 Draft 可 apply。
   - v2 Active 缺 evidence 被拒绝。
   - v2 Active 完整通过。
   - Promoted 缺 promoted_to 被拒绝。
   - v2 draft id 被 apply 重写为新 KNNN。
   - draft 内已有冲突 KNNN 被拒绝。
   - `last_reviewed` invalid / due / not-due。
   - `read_when` 命中和不命中。
9. 更新 README、System Manual、template。

### 验收标准

1. 旧 Knowledge 项目不被破坏。
2. 新 draft 默认生成 v2 metadata。
3. Active 高可信门槛可机械检查。
4. `knowledge sync` 能从 v2 metadata 同步索引。
5. 相似去重仍有效。
6. v2 front matter 中 `stale_after_days: 60` 或等价正整数字段有 parser/schema 测试覆盖。
7. source / evidence 在 Active/Promoted 下断链会失败，Draft 下只 warning。
8. `promote --dry-run` 不写 authority；`promote --apply` 只写白名单目标并可 check-after。
9. `knowledge apply` 正确处理 draft id：空缺或 `K-DRAFT` 会被重写为新 KNNN；冲突 KNNN 被拒绝。
10. `review stale` 覆盖 `last_reviewed` invalid、due、not-due 和 `--days` fallback。
11. `read_when` 推荐覆盖命中、不命中、Promoted redirect 和只匹配允许语料。
12. Draft 的断链 warning 不使 strict 失败，但会出现在 JSON warnings / skipped_items。
13. `uv run python -m unittest`、template check、strict check、minimal smoke 通过。

## 模块 3：结构化链接图与反向链接

### 目标

建立 ACF link graph，把普通 Markdown 导航链接和结构化治理关系区分开；反向链接作为派生导航信息，由 ACF 从 metadata 生成，不允许 agent 手写，且 Obsidian-friendly 但不依赖 Obsidian。

### 关系分类

普通 Markdown 链接：

```text
用于导航；ACF check 校验断链；不默认进入治理 backlinks。
```

结构化治理关系：

| 关系 | 默认 backlinks | 说明 |
|---|---|---|
| `promoted_to` | 是 | Knowledge 升格到 rules/ADR/manual/architecture |
| `supersedes` | 是 | 新对象取代旧对象 |
| `depends_on` | 是 | 稳定对象明确依赖另一对象 |
| `source` | 否，graph 可查 | 来源材料 |
| `evidence` | 否，graph 可查 | 测试、日志、WS、worklog 证据 |
| `derived_from` | 否，graph 可查 | 提炼来源 |
| `related` | 否 | 普通相关，默认不写 |

### 结构化关系目标规范

1. 结构化关系字段中的 target 使用规范化字符串，不使用 Markdown link 或 Obsidian `[[双链]]`。
2. 支持 context-root 相对 Markdown 路径、带 heading anchor 的 Markdown 路径和项目根内非 Markdown 证据路径。
3. 路径必须使用 `/`，不得使用绝对路径、Windows drive path 或 `file://`。
4. resolver 顺序为 context root 优先、当前文件目录次之、project root fallback。
5. JSON edge 必须输出 `source_file`、`field`、`relation`、`target`、`resolved_path`、`scope`、`fragment`、`line` 或 `metadata_key`。
6. 普通 Markdown 链接只进入 link check / rewrite，不默认生成治理 edge；所谓“结构化 Markdown links”第一版不实现，避免与导航链接混淆。

### Backlinks 写入策略

1. Backlinks 只写 generated block：

```markdown
## ACF 反向链接

<!-- ACF:LINKS:BACKLINKS-GENERATED:START -->
| 来源 | 关系 | 摘要 | 路径 |
|---|---|---|---|
| K001 | promoted_to | Workstream-first flow | [reference/knowledge/K001-workstream-first.md](../knowledge/K001-workstream-first.md) |
<!-- ACF:LINKS:BACKLINKS-GENERATED:END -->
```

2. 一个目标文件最多一个 backlinks block。
3. marker 外人工内容永不修改。
4. 无 marker 时默认不写，除非 `--init-marker <target> --apply`。
5. active/Context.md 默认不写 backlinks block。
6. rules/ADR/reference 高权威文件只允许显式 `--apply --target <path>`。
7. worklog/archive 默认不写 backlinks block。
8. Obsidian `[[双链]]` 不作为 ACF 机器输入；ACF 输出标准 Markdown 链接，让 Obsidian 自然识别。
9. 生成表格中的路径列必须渲染为相对目标文件的 Markdown link，并做 table cell escaping。
10. 关系删除后，下一次 sync 从 graph 重算 generated block，旧 backlink 行自然消失；dry-run JSON 必须报告 removed_edges_count。

### 命令需求

1. `acf links graph [path] --json`
   - Phase 1 只读扫描 Knowledge v2 metadata 的 `promoted_to`、`supersedes`、`depends_on`、`source`、`evidence`、`derived_from`、`related`。
   - ADR、Workstream metadata 和结构化 Markdown links 是 Phase 2，不在第一版 silently scan。
   - 输出 nodes、edges、broken_refs、summary。
2. `acf links check [path] --json`
   - 检查结构化关系目标是否存在。
   - 对 promoted_to/supersedes/depends_on 缺失目标在 strict 下 error；source/evidence 缺失至少 warning。
3. `acf links backlinks <target> [path] --json`
   - 查询目标文件被哪些对象引用。
   - 不写文件。
4. `acf links sync-backlinks [path] --dry-run --json`
   - 统一从 link graph 重算 backlinks block。
   - 默认只预览，不写文件；正式写入必须传 `--apply`。
   - 默认只更新已有 `ACF:LINKS:BACKLINKS-GENERATED` marker 的文件。
   - `--init-marker <target> --apply` 显式初始化单个 target；批量初始化必须使用 `--targets-file` 并排除 active、worklog、archive。
   - high-authority target 必须显式 `--apply --target <path>` 或 `--targets-file`；不能用隐式 graph 批量写。
   - `--targets-file` 中每个目标都必须逐项通过 authority / scope 检查，不能因为来自显式文件而批量豁免。
5. `acf links rewrite --moved old new [path] --json`
   - 文件移动后扫描 context 内 Markdown 文件，重写指向 old 的入站 Markdown link。
   - 同时重写 Knowledge v2 metadata 中指向 old 的结构化关系 target。
   - 跳过 fenced code、URI、Obsidian 双链和 generated backlinks block。
   - 保留 anchor、图片链接和空格路径 angle wrapping。
   - 支持 `--dry-run --json`；正式写入后 next_actions 提示运行 `links check` 与 `links sync-backlinks --dry-run`。

### 实现路径

1. 新增 `ai_context_framework/domains/links.py`：
   - node/edge 数据结构。
   - scanner。
   - target resolver。
2. 新增 `ai_context_framework/commands/links.py`：
   - graph/check/backlinks/sync-backlinks/rewrite。
3. 复用 `markdown.py` 的 link parser 和 relative link renderer；新增 inbound rewrite helper。现有 move rewrite helper 只可复用局部解析/渲染逻辑，因为它主要处理移动后文件内部出站链接，不覆盖全 context 入站链接。
4. 复用 `markers.py` 的 generated block helper。
5. 第一版只从 Knowledge v2 metadata 提取结构化治理关系；ADR/Workstream 后续扩展。
6. 增加 tests：
   - graph 提取 promoted_to。
   - graph 提取 source/evidence 但不写 backlinks。
   - backlinks 查询。
   - sync-backlinks 只替换 marker 内内容。
   - 无 marker 默认不写。
   - Obsidian `[[双链]]` 被忽略。
   - broken promoted_to 被 check 报告。
   - rewrite 更新全 context 入站 Markdown link 和 Knowledge metadata target。
   - rewrite 跳过 fenced code、URI、Obsidian 双链和 generated backlinks block。
7. 更新 System Manual、template manual、README 和 `reference/Generated_Marker_Sync_Design.md` 的 links/backlinks 说明；新增 `LINKS / BACKLINKS-GENERATED` marker 的 canonical domain / purpose 约定。但第一版实现 Workstream 不直接写高权威文件，只生成对应实施切片或 merge request。

### 验收标准

1. 普通 Markdown 链接和治理关系明确区分。
2. Backlinks 不产生手写重复。
3. 高权威文件不会被默认写入。
4. Obsidian 可读生成链接，但 ACF 不依赖 Obsidian。
5. 多 WS 并行时，WS 不直接抢写 backlinks；统一 sync 重算。
6. 文件移动后，入站 Markdown link 和 Knowledge metadata target 都能被 dry-run/rewrite/check 覆盖。
7. sync-backlinks 默认 dry-run，`changed_files == []`；没有 `--apply` 不写任何文件。

## 模块 4：Workstream guard 重设计

### 目标

把 guard 从“整个 dirty workspace 是否属于某个 WS”的排他检查，改为“给定变更文件是否符合 WS scope”的归属检查，支持同一工作区多个 agent / 多个 Workstream 并行修改不同文件。

### 当前问题

当多个 WS 同时执行且同一 repo 有多个 dirty files 时，`acf workstream guard WS001` 若检查整个 git working tree，会把 WS002 的变更也算到 WS001，导致误失败。

### 新语义

```text
Workstream scope 是变更归属契约，不是整个工作区锁。
```

guard 需要同时满足两个目标：共享工作区中不因其他 WS 的已声明 dirty files 误失败；当前 WS 的显式文件集仍必须被强校验，不能把真正越界写入降级成 warning。

### 命令需求

1. `acf workstream preflight WS003`
   - 开始前检查 scope 是否完整。
   - 检查与其他 Active WS 是否有 owned/assigned 冲突。
   - 检查 shared 是否有 merge_owner 或 serial coordination。
   - 检查 authority scope 是否符合 Workstream type。
   - 检查 workspace dirty files，但只把其他 Active WS 已声明的 dirty files 作为 warning；未归属 dirty files 必须进入 `unattributed_dirty_files`。
2. `acf workstream guard WS003 --file <path>` / `--files <paths...>`
   - 默认推荐模式。
   - 只检查传入文件是否在 WS003 write_scope 内。
   - 输出 in_scope_files、out_of_scope_files、authority_write_attempts。
   - 这是 ready/done 前最推荐的强验收模式。
3. `acf workstream guard WS003 --from-git`
   - 从当前 git diff 读取 changed files。
   - 当前 WS in-scope 文件强校验。
   - 匹配其他 Active WS owned/assigned scope 的 dirty files 进入 `other_workstream_dirty_files`，`ok: true`、warning、不失败，但 `authoritative_for_completion: false`。
   - 不匹配任何 Active WS scope 的 dirty files 进入 `unattributed_dirty_files`，`ok: false`、`error_code: workstream_guard_unattributed_dirty`、`authoritative_for_completion: false`。
   - 第一版不提供 advisory-only 参数；需要强验收时必须改用 `--file` / `--files` 显式文件集。
4. `acf workstream guard WS003 --workspace --strict-workspace`
   - 保留旧式排他检查，只适合 isolated worktree / 单 WS。
5. `acf workstream guard WS003 --owned-only`
   - 只允许 owned/assigned，shared 文件一律失败。
6. `acf workstream guard WS003`
   - 裸命令保留为兼容入口，新语义等同 `--from-git`。
   - 当存在 other / unattributed dirty files 时，next_actions 必须提示使用 `--file` 明确本次强验收文件集。
7. `--changed-file` 保留为 `--file` 的兼容 alias，至少一个版本周期不移除。

### Guard 模式矩阵

| 模式 | 文件来源 | 其他 WS dirty | 未归属 dirty | 是否可作为 ready/done 强证据 |
|---|---|---|---|---|
| `--file` / `--files` | 显式传入 | 不参与 | 不参与 | 是 |
| `--changed-file` | 显式传入 alias | 不参与 | 不参与 | 是 |
| 裸 `guard` | git diff | warning，`ok=true`，`authoritative=false` | `ok=false`，`workstream_guard_unattributed_dirty` | 仅在无 other/unattributed 时是 |
| `--from-git` | git diff | warning，`ok=true`，`authoritative=false` | `ok=false`，`workstream_guard_unattributed_dirty` | 仅在无 other/unattributed 时是 |
| `--workspace --strict-workspace` | git diff | `ok=false` | `ok=false` | 是，适合 isolated worktree |
| `--owned-only` | 与主模式相同 | shared fail | out-of-scope fail | 是，用于严格交付 |

### 输出契约

```json
{
  "schema_version": 1,
  "ok": true,
  "command": "workstream guard",
  "context": "docs/ai",
  "id": "WS003",
  "mode": "files",
  "authoritative_for_completion": true,
  "checked_files": [],
  "changed_files": [],
  "in_scope_files": [],
  "out_of_scope_files": [],
  "unattributed_dirty_files": [],
  "other_workstream_dirty_files": [],
  "conflicts_with_active_workstreams": [],
  "authority_write_attempts": [],
  "error_code": null,
  "message": "all checked files are in scope",
  "warnings": [],
  "next_actions": []
}
```

字段语义：

1. `changed_files` 表示 guard / preflight 命令实际写入的文件；guard 和 preflight 都是只读命令，因此必须恒为 `[]`。
2. `checked_files` 表示本次被校验的文件集；git diff 得到的 dirty files、显式 `--file` 文件和 strict workspace 文件都进入这里。
3. `authoritative_for_completion` 表示该结果是否可作为 ready/done 前强验证证据；存在 `other_workstream_dirty_files` 或 `unattributed_dirty_files` 时必须为 `false`。
4. `mode` 只允许 `files`、`from_git`、`workspace_strict`、`preflight`。
5. 失败时必须提供稳定 `error_code`、可读 `message` 和可执行 `next_actions`。

失败条件：

1. 传入文件 out_of_scope。
2. Task Workstream 直接写 authority path，永远失败；merge request / merge_targets 只记录候选影响范围，不授予写权限。
3. shared scope 缺 merge_owner 或 serial coordination。
4. strict-workspace 模式下存在不属于该 WS 的 dirty files。
5. `--from-git` / 裸 guard 下存在未归属 dirty files 时失败，并且不作为完成证据。
6. `evidence:` path 被修改但没有同时声明 `draft:` 或 `assigned:` 写权限。
7. 非 git workspace 下运行裸 guard / `--from-git` 时失败，返回稳定 error_code 和 next_actions，提示改用 `--file` / `--files`。

非失败 warning：

1. 共享工作区存在其他 dirty files，但未纳入本次 guard 文件集。
2. 文件属于 shared scope，需要 merge owner 协调。
3. 非 git workspace 下，显式 `--file` / `--files` 仍可 `ok=true` 强验收。
4. `--changed-file` alias 仍可用，但提示迁移到 `--file`。

### Scope 规则

| Scope type | 是否直接写权限 | 排他性 | 冲突检查 | 备注 |
|---|---|---|---|---|
| `owned:` | 是 | 仅本 WS | 与其他 Active owned/assigned 冲突 | 通常用于本 WS 详情 |
| `assigned:` | 是 | 单一 WS | 与其他 Active assigned/owned 冲突 | 用于明确分配的代码或文档 |
| `shared:` | 有条件 | 非排他 | 必须有 merge_owner 或 serial coordination | guard pass 时仍给 warning；`--owned-only` 下失败 |
| `draft:` | 是 | 可并行 | 文件名必须包含 WS ID 或可追溯 ID | 草案不进入默认读取路径 |
| `authority:` | 仅 Merge/Maintenance 可写 | 高风险 | Task WS 永远不能直接写 | `merge_targets` 不等于权限 |
| `evidence:` | 否 | 无 | 只可引用 | 如需写证据产物，使用 `draft:` 或 `assigned:` |

Authority 类型矩阵：

| Workstream type | authority path 直接写 | `authority:` scope | `merge_targets` |
|---|---|---|---|
| Task | 永远失败 | 不授予写权限 | 只记录候选合并目标 |
| Merge | 仅显式声明且 guard 通过 | 可写 | 指向本次合并目标 |
| Maintenance | 仅显式声明且 guard 通过 | 可写 | 指向维护目标 |

Scope path 规范沿用现有 Workstream front matter：context-root / project-root 相对路径、`/` 分隔、目录 scope 覆盖子路径、避免 glob 作为第一版强规则、Windows 路径先归一化再匹配。

## 模块 5：Workstream-first 入口、status 和 next-actions

### 目标

让 ACF 的日常入口反映真实使用：当存在 Active Workstream 时，agent 应自然从 Workstream 进入，而不是被 Empty Task_Plan / Current_Task 误导；同时通过 next-actions 降低命令选择成本。

### 查询输出契约

所有模块 5 查询命令必须输出稳定 JSON：

```json
{
  "schema_version": 1,
  "ok": true,
  "command": "status",
  "context": "docs/ai",
  "changed_files": [],
  "error_code": null,
  "warnings": [],
  "next_actions": []
}
```

规则：

1. 查询命令不得写文件。
2. `acf next` 不得触发任何 draft/report/archive 生成命令。
3. `next_actions` 只返回 1-3 条低风险、可执行命令。
4. `recommended_entry` 是首选入口对象；`next_actions` 是执行建议，两者不能互相矛盾。
5. 多候选时返回 `candidate_entries`，不随机选择单个 WS。

### 模块 5 JSON schema v1

`recommended_entry` 和 `candidate_entries[]` 使用统一对象结构：

```json
{
  "kind": "workstream_context",
  "command": "acf workstream context WS003 docs/ai --json",
  "reason": "single Active Workstream",
  "priority": 1,
  "workstream_id": "WS003",
  "status": "Active",
  "detail": "active/workstreams/WS003.md"
}
```

字段规则：

1. `kind` 枚举：`workstream_context`、`workstream_next_actions`、`workstream_dashboard`、`task_plan`、`review_stale`、`feedback`、`doctor`、`draft_status`、`none`。
2. `priority` 从 1 开始升序；`candidate_entries` 必须按 priority、status priority、id 稳定排序。
3. Workstream 摘要对象统一字段：`id`、`status`、`title`、`owner`、`detail`、`current_stage`、`type`。
4. `active_workstreams`、`ready_to_merge`、`blocked_workstreams`、`merging_workstreams`、`terminal_retained_workstreams` 都使用 Workstream 摘要对象数组。
5. 模块 5 的 `next_actions` 使用对象数组，不再只依赖字符串：`command`、`reason`、`risk`、`writes`、`requires_human`。查询命令本身不得写文件；推荐项必须准确标注 `writes`，写入建议允许 `writes: true`，并必须说明风险和是否需要人工确认。
6. 所有模块 5 查询命令应复用同一个 query payload builder，保证 `changed_files: []`、`warnings`、`error_code`、`next_actions` 字段一致。

### 命令需求

1. `acf status --json` 增强：
   - `workstream_state`
   - `active_workstreams`
   - `ready_to_merge`
   - `blocked_workstreams`
   - `merging_workstreams`
   - `terminal_retained_workstreams`
   - `recommended_entry`
   - `candidate_entries`
   - `next_actions`
   - `workstream_state` 枚举：`NotInitialized / Inactive / ActiveClassPresent / Ambiguous / Invalid`
2. `acf workstream context WS003 --json` 增强：
   - required / recommended / optional / avoid_by_default 读取建议。
   - 当前 stage。
   - read_scope / write_scope。
   - 相关 Knowledge read_when 匹配结果。
   - guard 推荐命令。
   - merge/ready/done 条件缺口。
   - required 必须包含 WS 详情；recommended 来自 read_scope 和匹配的 Active Knowledge；optional 可含 worklog / evidence；avoid_by_default 包含 draft、archive、完整 worklog 和原始日志。
3. `acf workstream next-actions [WS003] --json`
   - 单 WS 或全部 Active WS。
   - 判断下一步是 stage、guard、merge-request、ready、done、archive 还是 scope-add。
   - 输出原因和可执行命令。
   - Active：推荐 stage/focus/guard/scope-add/merge-request。
   - Blocked：推荐查看 blocker 或解除阻塞，不推荐 ready/done。
   - ReadyToMerge：推荐 merge review、merge-start、返工或 done --merge-resolution。
   - Merging：推荐完成合并、补 merge_resolution 或转 Done。
   - Done/Cancelled retained：推荐 archive-candidates / archive-draft / archive 或补 keep-active metadata。
4. `acf next [path] --json`
   - 全局下一步入口。
   - 聚合 status、doctor、review stale、feedback、draft、workstream dashboard。
   - 输出 1-3 条低风险建议。
   - 只调用或复用只读摘要；不生成 doctor report、semantic draft、curation draft、writeback draft 或 archive draft。
   - 不读取 archive 正文、draft 正文或完整 worklog。
5. `acf draft status [path] --json`
   - 列出 writeback / curation / knowledge / archive drafts。
   - 不读取正文，只列类型、年龄、路径、建议动作。
   - draft type 枚举：`writeback`、`doctor_semantic`、`curation`、`knowledge`、`archive`。
   - draft 类型路径：`worklog/writeback-drafts/`、`worklog/writeback-drafts/*-doctor.md`、`worklog/knowledge-drafts/`、`worklog/archive-drafts/` 和 curation draft 路径。
   - 年龄来源优先文件名 ISO date，fallback 到 mtime；不得读取正文推断状态。

### recommended_entry 决策优先级

1. 存在多个 Active-class Workstream：推荐 `acf workstream dashboard --json`，并列出 `candidate_entries`。
2. 存在单个 Active-class Workstream：
   - Active -> `acf workstream context WSxxx --json`。
   - Blocked -> `acf workstream next-actions WSxxx --json`，优先 blocker。
   - ReadyToMerge -> `acf workstream next-actions WSxxx --json`，处理 merge / reject / no_merge_required / done。
   - Merging -> `acf workstream next-actions WSxxx --json`，处理 merge completion / merge_resolution / Done。
3. 存在 Done/Cancelled retained Workstream 且无 Active-class WS：推荐 `acf workstream archive-candidates --json` 或 `acf workstream next-actions WSxxx --json`。
4. 无 Active-class Workstream 且 Task_Plan Active：推荐 Task_Plan / Current_Task。
5. Task_Plan Empty 且无 Active-class WS：推荐 review stale / feedback / doctor 只读摘要，或报告无当前执行入口。
6. 用户显式指定 WS 时，用户消息优先，但仍返回冲突 warning。

### 实现路径

1. 先实现 `workstream next-actions`，因为它最贴合真实使用日志。
2. 先实现或复用统一 query JSON payload builder，保证模块 5 查询命令字段、排序和 `changed_files: []` 一致。
3. 再增强 `status`，把 Workstream 状态暴露到总入口。
4. 再增强 `workstream context`，与 Knowledge v2 read_when 集成。
5. 最后实现 `acf next` 和 `draft status` 聚合入口。
6. tests：
   - 精确 schema 断言：recommended_entry、candidate_entries、next_actions 对象字段和排序稳定。
   - 无 WS 时 status 不增加噪音。
   - Active WS 时 recommended_entry 指向 workstream context。
   - Task_Plan Empty + 单个 Active WS 时，recommended_entry 指向 workstream context。
   - 多 Active-class WS 时不随机选择单个 WS，推荐 dashboard 并返回候选。
   - Blocked 不推荐 ready/done。
   - ReadyToMerge 提示合并审查、merge-start、返工或 done --merge-resolution。
   - Done 缺 merge_resolution 由 next-actions / check / audit 提示补齐。
   - Merging 推荐完成合并或补 merge_resolution。
   - 单个 Merging Workstream 的 recommended_entry 指向 workstream next-actions。
   - Done/Cancelled retained 的 recommended_entry 指向 archive-candidates 或 workstream next-actions。
   - Draft status 不读取正文。
   - Knowledge read_when 匹配只推荐 Active Knowledge。
   - `acf next --json` changed_files 为空且不创建 draft/report/archive 文件。
   - 预置 draft/report/archive sentinel，运行 `acf next` 后断言文件集合、mtime 和 `changed_files == []` 都不变。

### 验收标准

1. Task_Plan 为空时不会误导 agent 认为项目无任务。

4. 不把 draft 或 archive 加入默认读取路径。
5. 多 WS、Blocked、ReadyToMerge、Merging、Done retained 都有明确推荐分支。
6. 所有查询命令 JSON 契约一致，且 `changed_files == []`。
7. `recommended_entry`、`candidate_entries` 和对象化 `next_actions` 有稳定 schema 与排序测试。
