### 现有工具缺口

1. `upgrade` 目前只补齐结构和少量可管理文档，不会给出“这个项目是否适合升级、升级后还需要修什么”的分层计划。
2. `check --strict` 能发现问题，但输出是通用健康检查；它不会把问题组织成升级阶段、阻塞等级、可自动修复项和人工判断项。
3. `status` 在多 Active Workstream 时会进入 `Ambiguous`，这对单主线任务合理，但真实 dogfooding 中多个并行 WS 是常态；升级预检需要把“多 active 本身”和“非法 stage/过期终态保留”分开。
4. usage event 当前没有直接保存 `project_root`，全局日志只能用 project id、事件、扫描路径和 hash 反推真实项目；这会降低“全局升级盘点”的可解释性。
5. 现有 upgrade matrix 重点覆盖旧结构兼容和幂等，不足以覆盖真实项目出现的占位符污染、断链、workstream lifecycle 债务、日志盘点和非标准路径。

### 外部参考原则

本 Workstream 借鉴但不绑定外部工具：

1. Terraform 官方 `plan/apply` 思路：先生成可审阅执行计划，再 apply；speculative plan 不能替代 apply 前复核。参考：<https://developer.hashicorp.com/terraform/cli/commands/plan>
2. Terraform `apply` 思路：apply 会基于计划执行实际变更，自动批准应谨慎。参考：<https://developer.hashicorp.com/terraform/cli/commands/apply>
3. Kubernetes `kubectl diff` 思路：写入前给出差异视图，帮助审查将要改变什么。参考：<https://kubernetes.io/docs/reference/kubectl/generated/kubectl_diff>

ACF 的迁移对象是 Markdown 上下文，不是基础设施或数据库，因此不能照搬强制 apply；应以非破坏式结构补齐、语义问题草案化、人工/agent 审阅为主。

## 需求定义

### 核心目标

让任意旧版本 ACF 项目可以稳定升级到当前框架结构，同时保证：

1. 旧项目已有权威内容不丢失。
2. 临时发现、历史过程、模板占位符、过期 workstream 和断链不会被升级过程误写成当前事实。
3. AI agent 能拿到“范围恰当、权威、足够完成当前任务”的上下文，而不是被旧结构和历史噪音污染。
4. 升级路径可预检、可解释、可重复执行、可测试。

### 必须覆盖的旧项目形态

1. 没有 ACF context 的项目。
2. 旧 minimal context。
3. 旧 standard context 缺 `human/`、`archive/feedback/`、`reference/knowledge/`、`worklog/knowledge-drafts/`。
4. 缺 `Feedback_Inbox.md`、`Task_Plan.md`、`Knowledge_Index.md`、`Archive_Index.md` 或 `Context_Curation_Prompt.md`。
5. 自定义过的 `AGENTS.md`、`Project_Rules.md`、`System_Manual.md`，不能安全整体替换。
6. 结构已经是新版本，但仍有大量模板占位符。
7. 结构已经是新版本，但存在断链、重复当前事实、多 Active 子任务。
8. 旧项目已有 Active `Current_Task.md` 或 `Task_Plan.md`，升级不能覆盖或自动归档。
9. 未启用 Workstream 的旧项目，升级不能默认启用 Workstream。
10. 已启用 Workstream 的项目，覆盖无 active、单 active、多 active、ReadyToMerge、Merging、Done/Cancelled 保留、`keep_active_until` 过期、非法 stage id、缺 evidence、scope 重叠。
11. 非标准 context 路径，例如 `ai/`、`docs-acf/ai/` 或历史临时目录。
12. root `AGENTS.md` 缺失、旧转发、手写自定义。
13. 已存在 generated marker、旧 upgrade marker、重复 marker 或 marker collision。
14. upgrade draft、curation draft、archive draft 已存在时的幂等和拒绝策略。
15. 项目没有 git、git dirty、CRLF、Unicode 路径、中文文件名。
16. 全局日志中存在真实项目、旧事件无 `project_root`、测试/临时项目、已删除项目、重复项目 id 不可能但需防御。

## 设计方案

### 总体策略

采用四阶段升级模型：

1. **Inventory**：从全局 usage log 和磁盘扫描识别候选项目，区分真实项目、测试项目、模板、归档临时上下文和已删除路径。
2. **Assess**：对单个 context 生成升级评估，合并 `status`、`check --strict`、`upgrade --dry-run`、workstream lifecycle、marker 和上下文路径信号。
3. **Apply Structural Upgrade**：继续使用现有 `acf upgrade [target] --check-after --json` 做非破坏式结构补齐和可管理文档刷新。
4. **Curate Semantic Debt**：对占位符、断链、过期 workstream、多 Active 子任务、旧 handoff 等语义债务只输出草案和 next actions，不自动改事实。

### CLI 设计

保持当前 `acf upgrade [target]` 兼容，不把 `upgrade` 改成破坏性迁移器。

新增或扩展命令：

1. `acf upgrade [target] --plan --json`
   - 只读；不写项目文件，不写真实或临时 usage log。
   - 输出单项目升级计划。
   - 包含 `readiness`、`risk_summary`、`findings`、`structural_changes`、`manual_actions`、`recommended_commands`。
   - 与 `--dry-run`、`--check-after` 互斥；冲突时返回 `ok=false`、`error_code=input_error`、exit 2。
   - 如果 target 不是 ACF context 且无法发现 `docs/ai` / `docs-acf/ai`，返回 `ok=false`、`error_code=context_not_found`、`readiness=blocked`、exit 1，并给出 `acf init` next action。
2. `acf log projects --json`
   - 只读。
   - 汇总用户级 `ACF_HOME/projects/*/logs/usage.jsonl`；`log` 命令本身继续不记录 usage event。
   - 输出 raw log count、event count、按项目 id 聚合的 first/latest/commands/error_count。
3. `acf log projects --scan-root PATH --json`
   - 可重复传入 `--scan-root`。
   - 扫描真实 context root，按 `usage_project_dir(infer_project_root(context))` 匹配旧日志 project id。
   - 输出 `resolved_project_root`、`context_root`、`context_profile`、`classification`。
4. `acf log projects --log-root PATH --json`
   - 只读指定 ACF home 或 `projects` 目录，用于测试、审计备份日志或避免依赖当前环境变量。
   - 不改变 `ACF_HOME`，不创建缺失目录。
5. `acf log projects --min-events N --include-unresolved --json`
   - `--min-events` 只过滤 `projects` 列表，不改变 raw summary count。
   - 默认不在 `projects` 列表展开 unresolved log-only 项目；`--include-unresolved` 时展开，避免真实项目列表被测试夹具淹没。
   - synthetic/test-like 项目不从 raw count 删除，只在 `classification` 和 summary 中单独计数。

### 退出码与只读日志契约

1. `upgrade --plan` 成功生成计划时 exit 0，即使 `readiness=blocked`；此时 `ok=true` 表示“计划生成成功”，不是“项目健康”。
2. 找不到 context、参数互斥、JSON 生成失败等命令级错误时 `ok=false` 并使用非零 exit。
3. finding `severity` 枚举为 `info`、`warning`、`error`、`blocking`；`blocking_count` 只统计 `blocking`。
4. `safe_apply=true` 仅表示可以运行结构性 `acf upgrade --check-after --json`，不表示语义债务已清理。
5. `usage_loggable()` 必须跳过 `upgrade --plan`，并新增测试断言该命令不会向默认 `ACF_HOME` 写入 usage event。
