## 有价值的结论

- `release_check --mode full` 在本机会话里前台运行会因长时间无输出被判空闲中断；改为后台 `nohup` + 轮询日志后，用 `--skip-tests --skip-upgrade-matrix` 单独跑构建与隔离安装段（unittest 与 `upgrade_matrix --mode full` 已分别跑绿），避免整体空转。
- `dist/` 残留历史版本制品会让 `artifact_files` 报 `expected exactly one wheel and one sdist`；发布验收应省略 `--output-dir` 走临时目录，防止历史 dist 混入当期制品判定。
- 发布闭合的决策顺序仍应是「验收 → 碰撞探测 → tag → 发布」：本次在授权前只完成前两步，tag 与发布保持未执行，避免出现 CHANGELOG 已写"发布完成"而实际未落地的假事实。

如果这些结论已经成为当前事实，请同步更新到 `active/Context.md`。

## 无效尝试

- v0.0.3.99 首次发布尝试失败：**发布态 gap** —— 提交 `5a24ce3` 与不可变 tag `v0.0.3.99` 已推送到远端，release workflow #41 触发成功，但其必需门禁 `Required CI before publish / Tests (windows-latest, Python 3.12)` 的「Unit tests」步骤在 22m33s 后失败，`Build, verify, and publish` 被 skipped，**PyPI 未产生 0.0.3.99**（`info.version` 仍为 `0.0.3.98`）。
- 同一 commit `5a24ce3` 在同一分钟触发的 master push CI（run 35773751779）里，`Tests (windows-latest, Python 3.12)` 成功（24m15s），ubuntu 两个版本与 windows 3.10 也全部成功；因此这次失败不是确定性回归。
- 本机复现尝试均未命中：Python 3.12 下单独跑新增的 `tests.test_continuation_handoff_takeover`（29 项，73s）全绿；用两个并发实例压测历史同源可疑套件 `tests.test_worktree_resilient_merge`（各 19 项、各 ~490s）也全部 OK。
- 结论对齐 2026-09-20 的同类记录：Windows 上 worktree 关闭的「临时目录被刚终止进程瞬时占用」是发布门禁的偶发噪声源，历史上判定为可自愈的噪声。**但「可自愈」的前提是能在 Actions 页面 Re-run failed jobs**；本机没有任何 GitHub 登录凭据（无 `gh`、API 日志需登录、页面提示无法执行该操作），同名 tag 又不可重建，因此自治推进的唯一合规路径是「升版到新的不可变 tag」。据此用 `acf version set v0.0.3.100` 收敛四处版本（内容与 `5a24ce3` 完全一致），`v0.0.3.99` 保留为历史失败 release tag。
