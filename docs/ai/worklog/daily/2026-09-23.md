## 有价值的结论

- `release_check --mode full` 在本机会话里前台运行会因长时间无输出被判空闲中断；改为后台 `nohup` + 轮询日志后，用 `--skip-tests --skip-upgrade-matrix` 单独跑构建与隔离安装段（unittest 与 `upgrade_matrix --mode full` 已分别跑绿），避免整体空转。
- `dist/` 残留历史版本制品会让 `artifact_files` 报 `expected exactly one wheel and one sdist`；发布验收应省略 `--output-dir` 走临时目录，防止历史 dist 混入当期制品判定。
- 发布闭合的决策顺序应是「验收 → 碰撞探测 → tag → 发布 → installed-state 回写」：CHANGELOG/README 里"当前版本"这类陈述必须以 PyPI 事实为准，未上线前不能写成已完成；本次 `v0.0.3.99` 从未进入 PyPI，因此相关陈述最终落到了真正上线的 `v0.0.3.100`，`.99` 只在文档里作为失败 release tag 保留。
- 外部 CI 结论可以公开只读核对（Actions REST API 的 runs/jobs 不需要登录即可读 name/status/conclusion），但 job 日志与 Re-run 动作必须登录。因此"本机可判断最终发布状态"与"本机可原地重跑失败作业"是两件事：前者可用 PyPI 作证据，后者仍需账户所有者在网页操作——这也是本次不得不消耗一个新版本号的原因。

如果这些结论已经成为当前事实，请同步更新到 `active/Context.md`。
