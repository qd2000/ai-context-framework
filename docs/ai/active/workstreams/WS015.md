## 当前发现

无。

T006 仅剩外部动作：本地版本、门禁与制品验证全部完成，但 commit / tag / push（触发 PyPI）与全局安装更新等待用户明确授权；`v0.0.3.93` 的 Actions run 结论同样需要用户在仓库侧确认，不能用历史记录推断。

Release 触发已执行：commit `93f04fd` 与 tag `v0.0.3.94` 已推送 origin（`refs/tags/v0.0.3.94 -> 93f04fd`）。推送后约 18 分钟 PyPI 仍无 `0.0.3.94`（latest=`0.0.3.92`），而 `v0.0.3.93` 自推送后约 7 小时仍未发布，指向同一个未闭合的发布审批/流水线门，而非本次变更的代码问题（本地 wheel+sdist 已隔离安装验证通过）。

GitHub Actions 实证（用户提供 run 列表）：v0.0.3.94 run #36 失败 25m57s、v0.0.3.93 run #35 失败 21m39s、v0.0.3.92 run #34 成功仅 3m48s。v0.0.3.92 时代 release.yml 尚无 verify 作业，WS014 加入 verify（复用 ci.yml）后两次发布均在约 20+ 分钟后失败，说明 CI 门禁自 WS014 起就未通过，且 v0.0.3.93 的失败早于 WS015 改动。当前受阻原因是 CI 门禁失败而非 environment 审批；需要失败 job/step 日志才能定位。

Windows CI 门禁根因已定位并修复（既有缺陷，非 WS015 引入）：hosted runner 的临时目录以 8.3 短路径（`RUNNER~1`）暴露，而 ACF/安装脚本使用规范长路径（`runneradmin`）。`tests/test_worktree_resilient_merge.py` 的 overlap 竞态用 `Path(source) == primary` 判断注入点，别名不一致导致注入从未发生、本应被阻断的合并被误判为通过；`tests/test_install_scripts.py` 用裸字符串比对 `acf.cmd` 中的 python.cmd 路径；`tests/test_continuation_execution.py` 的 tearDown 受已终止进程句柄瞬时占用影响。三处均改为文件身份比较或规范路径 / 有界重试，并已在本机用 `GetShortPathNameW` 构造 8.3 别名条件复现验证（4 + 19 + 18 项通过）。
