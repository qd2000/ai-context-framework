## 当前发现

- 起点：`uv run acf doctor` 报告 2 条告警（`archive_index_missing_workstream`、`archive_index_generated_block_out_of_sync`），指向 `docs/ai/archive/Archive_Index.md` 生成块与归档文件不同步。2026-09-23 的 WS019/WS020 收口已明确「属既有漂移，本轮不自动 repair」，本次专门一次性收尾。
- 只读复算（用 runtime 聚合下的 `collect_archive_sync_rows` + `skipped_missing_generated_archive_details` + `render_archive_index_table` + `replace_generated_marker_block`，未落盘）得到 planned 与当前文本的统一 diff 只有 19 行，共三类差异：新增一行 ID `ws013-observer-retirement-and-v0.0.3.92-plan`、WS014/WS015/WS016 三行「原路径」由 `无。` 归一为 `active/Task_Plan.md`、WS019 的 Task/Plan 两行按 source_path 归一后重排。
- 「原因」列不丢：planned 文本中全部手写原因与原文件逐字一致，因此走 `--fix safe` 是安全的。
- 改动面已锁定：`acf archive sync --dry-run` 的 `changed_files` 只有 `docs/ai/archive/Archive_Index.md`；`check.py::check_archive`（`check.py:295-308`）确实会解析整份索引的所有表格行（含 END 标记之后的历史手写表格）校验日期与引用，因此新增行必须指向真实文件；我们不动生成块之外的内容。
- 顺带定位到两个**产品侧候选**（本次不改代码，只记录）：
  1. `runtime_parts/archive_workstream.py:73` 的 `update_archive_index()` 对每次归档写死 `source_path="无。"`，而 sync 渲染器从第 102-103 行使用的 `row["source_path"]` 是从归档文件恢复出的 `active/Task_Plan.md` / `active/Current_Task.md`；两边不一致意味着**每执行一次归档命令就会产生一次必然漂移**，这是本次三类差异里「原路径」列那一类的根因。
  2. `runtime_parts/doctor.py:543-585` 两条 finding 的 evidence 无论实际差异多小，都会把全部 workstream 行（20 条）与全部 Task/Plan 行（44 条）逐条列成 "should include"，导致告警看起来像「整份索引都缺失」，与实际「缺 1 行 / 3 列不一致 / 2 行重排」不符。
