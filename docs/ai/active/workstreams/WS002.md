## 当前发现

### 规划结论

本 Workstream 采用一次性完成模块化迁移，但实施过程必须分阶段验证。目标不是重写业务逻辑，而是把 `acf.py` 中已经稳定的命令实现迁移到职责清晰、agent 友好的 package 结构中。

关键判断：

1. `acf.py` 当前约 1.5 万行，已经超过 agent 低上下文维护的合理规模。
2. 拆分收益主要是降低后续 agent 读取范围、减少误改、降低并行开发冲突。
3. 本轮必须保持行为零变化：命令、参数、JSON 字段、错误码、退出码和模板产物都不得因拆分改变。
4. 本轮不实现 F017 / F019，不新增业务能力，不改变 ACF 上下文语义规则。
5. 当前基线版本为 `v0.0.3.48`；本 Workstream 不改变版本号，只迁移版本事实的代码位置与同步逻辑。

### 依赖方向

允许依赖方向：

```text
acf.py -> ai_context_framework.cli
cli.py -> commands/*
commands/* -> domains/* / validators/* / json_contract / paths / templates / observability
domains/* -> models / paths / markdown / tables / front_matter / locks / markers
validators/* -> domains/* / templates / models / json_contract
shared foundation -> Python stdlib only or lower-level shared foundation
```

禁止依赖方向：

1. `commands/*` 之间互相循环依赖。
2. shared helper 反向 import command module。
3. 新 package 内部 import 顶层 `acf.py`。
4. 为了拆分临时引入第三方运行时依赖。
5. 把跨领域业务逻辑塞回 `cli.py`、`commands/*`、`constants.py` 或新的 `common.py` / `utils.py`。

如果一个 command 需要复用另一个 command 的领域逻辑，必须先下沉到 `domains/*` 或 `validators/*`，再由两个 command handler 分别调用；不允许 command handler 互相 import。

### 版本迁移规则

1. WS002.1 到版本命令迁移前，`acf.py` 仍是唯一源码版本事实；不得在 `version.py` 中提前放置独立 `VERSION` literal。
2. `ai_context_framework/version.py` 与 `commands/versioning.py` 必须在同一个阶段迁移：引入 `VERSION = "v0.0.3.48"` 的同时，迁移 `version show/set` 的读写逻辑和测试。
3. 版本迁移完成后，`ai_context_framework/version.py` 是源码 checkout 的唯一版本事实。
4. 最终 `acf.py` 必须从 `ai_context_framework.version` re-export `VERSION`，保证 `import acf; acf.VERSION` 兼容。
5. `version show` 在源码 checkout 中读取并报告 `ai_context_framework/version.py`、`pyproject.toml`、`uv.lock`、`ai_context_framework.egg-info/PKG-INFO`；不再把薄 `acf.py` 当作版本事实文件。
6. `version set` 必须同步更新 `ai_context_framework/version.py`、`pyproject.toml`、`uv.lock`、`ai_context_framework.egg-info/PKG-INFO`。
7. installed package 下的 `acf --version` 使用导入态 `VERSION`；源码一致性检查只在可定位项目根目录时执行。

### 打包迁移规则

1. 最终 console script 使用 `acf = "ai_context_framework.cli:main"`。
2. `acf.py` shim 仍作为 `py-modules = ["acf"]` 或等价配置随包发布，用于 `python acf.py`、`python -m acf` 和 `import acf` 兼容。
3. `ai_context_framework`、`ai_context_framework.commands`、`ai_context_framework.domains`、`ai_context_framework.validators` 必须进入 wheel。
4. template 安装方式必须继续覆盖源码态和安装态；`templates.py` 负责 `ROOT/template` 与 `sysconfig.get_path("data")/share/ai-context-framework/template` 两种发现路径。
5. `tests/test_cli.py` 中旧发布形态断言必须从“必须是 `acf:main` + `py-modules = ["acf"]`”迁移为“console script 指向 package 入口、shim 仍可导入、template data 完整”。

### 行为不变检查

1. `uv run acf ...` 必须继续工作。
2. `uv run python acf.py ...` 必须继续工作。
3. `project.scripts` 中 `acf` 的入口必须更新到可安装 package 入口，或保持兼容且可安装后运行。
4. `scripts/minimal_smoke.py` 和 `scripts/upgrade_matrix.py` 中直接调用 `acf.py` 的路径需要继续可用。
5. `uv run acf --help` 和关键子命令 `--help` 的退出码必须保持成功。
6. `tests/test_cli.py` 不应大规模重写；现有测试作为行为锁，但旧单文件发布形态断言必须改成 package 发布形态断言。
7. `acf version set/show` 必须按“版本迁移规则”同步版本事实，不能继续扫描薄 `acf.py`。

### Agent 友好验收

1. 顶层 `acf.py` 小于 100 行。
2. 新模块单文件原则上小于 2,000 行；复杂领域首版可放宽到 3,000 行以内，但必须在 `Codebase_Structure.md` 标明后续拆分边界。
3. `Codebase_Structure.md` 必须列出“修改某类功能应读取哪些文件”。
4. 新增命令时应有明确落点，不允许继续把实现加回 `acf.py`。
5. 不允许出现“所有东西都进 common.py / utils.py / constants.py”的新巨型模块。
6. `commands/*` 只处理 CLI 适配；复用逻辑应在 `domains/*`、`validators/*` 或明确 shared foundation 中。

### 回滚策略

1. 每个阶段完成后运行 targeted tests；失败时只回退当前阶段迁移，不回退此前已验证阶段。
2. 如果 parser 行为出现不兼容，优先保持 `cli.py` 对旧命令结构兼容，而不是改测试适配新行为。
3. 如果 domain module 迁移暴露循环 import，优先下沉依赖到 shared helper，不让 command module 互相 import。
4. 如果打包后模板路径发现失败，优先修复 `find_template_dir()` 和 package data，不改模板目录结构。
