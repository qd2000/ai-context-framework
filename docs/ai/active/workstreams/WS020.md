## 当前发现

- 产品侧已经足够健壮：`ai_context_framework/worktree_service.py:1187 _close_remove_worktree_with_retry` 与 `:1238 _close_delete_branch_with_retry` 都是「`git worktree remove` + `retry_delay` 指数退避 + 超时抛 `worktree_close_timeout`」的有界重试；因此在 CLI 侧再包一层重试属于低价值的二次包装，本次不改产品行为。
- 真正的残留脆弱点在测试夹具：`tests/test_install_scripts.py` 的 live tool process 用例把 `ping.exe` 复制成临时根内的 `python.exe` 并 `Popen` 启动，原实现只用 `terminate()/wait(5)/kill()` 就退出 `TemporaryDirectory`；Windows 映像 Section 与目录句柄释放是异步的，这正是 2026-09-19 记录的「终止进程句柄瞬时占用」同一形态（那次只修了 `samefile` 断言，没有处理删除竞态）。
- `tests/test_continuation_execution.py` 已有一个私有 `_cleanup_tempdir`（15s deadline / 0.25s 退避），属同一逻辑的重复实现；抽出为共享 helper 后，它的进程树用例仍能借统一契约补上「父进程退场确认」。
- `tests/worktree_scenarios.py` 的 `TemporaryWorktreeScenario.close()` 直接 `cleanup()`，却是 worktree 类测试的公共入口（test_worktree_status / merge_contracts / collision / artifacts / cli 等模块共用），改一行即可让整批受益。
- 关键取舍依据：`MANIFEST.in` 只 include CHANGELOG / LICENSE / template / docs 与部分 scripts，**tests 完全不进 sdist 与 wheel**，因此测试夹具修复对用户可见产物零影响 —— 不 bump 版本、不打 tag、不发布，只提交 master 让真实 Windows runner 充当验收回路。

## 输出物

1. `tests/windows_teardown.py`：测试专用清理助手。三个公开入口 `terminate_and_wait`（terminate → 有界 wait → kill → PID 轮询确认退场）、`cleanup_temporary_directory`（先退场再重删临时根）、`resilient_rmtree`（幂等 + 有界退避）；另有 `temporary_root` 返回父目录已 resolve 的规范临时根，避免 8.3 短名别名。`sleep` / `monotonic` / `pid_probe` / `rmtree` 全部可注入。
2. `tests/test_windows_teardown.py`：16 项注入式单测（无需真实时间与真实进程，1.26s 跑完），覆盖首删成功返回 0、退避次数与 sleep 序列、deadline 耗尽后仍抛原始 `PermissionError`、非可重试异常立即透传、进程先于清理退场的顺序、路径已消失的幂等。
3. 四处高危夹具收编：`tests/test_install_scripts.py`（进程映像就在临时根内，改用退场确认 + 有界重删）、`tests/test_continuation_execution.py`（删除私有 `_cleanup_tempdir`，改为共享实现并给进程树用例补父进程退场确认）、`tests/worktree_scenarios.py`（`TemporaryWorktreeScenario.close()` 改为有界重删，覆盖 worktree 批次公共入口）、`tests/test_release_license_metadata.py`（`uv build` 产物落在临时根，改为同上清理）。
