ADR：ACF Core 与 Operations Control Plane 的边界

## 状态

Active

---

## 日期

2026-09-18

---

## 背景

顶层设计声明 ACF 不做 agent runtime、不做 scheduler 并保持 Markdown-first，但 continuation 已包含 owner lease、generation fencing、directive/effect journal、process identity、physical execution supervisor、heartbeat/renew、challenge/reconcile/recover、workspace provenance、closeout authorization、local capability、migration 与 issue aggregation，实质已接近外部 agent 执行控制面。同时 F019 反馈多 agent / 多 workstream 并行使用流程过重。为消除产品定位模糊，需要正式定义边界，而不是默认所有能力都属于同一个产品层。

---

## 问题

1. 设计文档说“不做 runtime / scheduler”，但仓库的代码、测试与 dogfooding 复杂度主要来自 runtime-like 控制面，产品定位长期模糊。
2. 不使用 continuation 的项目无法明确“哪些能力与我无关”，Operations 能力默认被当成 ACF 核心。
3. 后续 runtime 解耦（`runtime.py` 双向全局注入）缺少正式的边界依据，容易被误当作版本内小修复顺手重构。
4. 部分行为策略（例如“mission 保持 open 时先主动搜索安全替代工作”）被写进产品合同，但它们实际属于调度或项目治理策略。

---

## 决策

采用两层边界：ACF Core 只负责 Markdown-first 的上下文治理，continuation / worktree / closeout authorization / usage log / execution-effect-recovery 构成可选 ACF Operations 控制面。Core 不得依赖 Operations 状态，Operations 可独立关闭或独立打包，且不继续吸收项目业务策略。

完整分层与硬约束见本文「分层定义」与「硬约束」小节。

---

## 分层定义

### ACF Core

- Markdown context 与 template 生成、简化与检查。
- `init`、`status`、`check`、`upgrade`、`simplify`。
- `plan` / `task` / Task Stage。
- Workstream 文档模型与索引（详情 front matter 是事实源）。
- `archive` / `knowledge` / `edit` / `link`。
- 人工可审阅事实治理：ADR、rules、feedback inbox、worklog。

### ACF Operations

- worktree 生命周期。
- continuation：owner lease、generation fencing、directive / effect journal、workspace provenance、physical execution、challenge/reconcile/recover。
- closeout authorization ledger。
- usage log 与跨项目 issue 台账。
- 与 execution / effect / recovery 相关的用户级运行态。

---

## 硬约束

1. Core 不得依赖 Operations 状态；关闭或删除 Operations 后 Core 仍可独立工作。
2. 不使用 continuation 的项目不得承担额外默认负担。
3. Operations 的 JSON 与运行态不是项目事实源。
4. Operations 必须能在未来独立打包或整体关闭。
5. Operations 不继续吸收项目业务策略；行为策略属于 Scheduled Task wrapper、项目规则或外部 supervisor contract。
6. 本 ADR 只约束逻辑分层与依赖方向，不要求在本版本拆成两个 PyPI 包，也不改变现有命令入口与文件布局。

---

## 理由

1. 明确 ACF 分为 Markdown-first 的 Core 与可选 Operations 控制面两层：Core 不依赖 Operations 状态，Operations 可独立关闭或独立打包。
2. 消除“设计说不是 runtime、实现却像 runtime”的定位模糊，让新能力必须先判断归属。
3. 为后续 runtime 解耦提供决策依据：export allowlist → 显式 RuntimeContext → parser composition → 收敛 `acf.py` shim，作为独立 Workstream 推进。
4. 为 F019 的多 agent / 多 Workstream UX 反馈提供边界输入。
5. 该决策已经进入项目维护流程，需要成为可追溯事实。

---

## 考虑过的替代方案

### 方案 A：只更新索引，不生成 ADR

优点：

- 文件更少。
- 短期维护成本更低。

缺点：

- 缺少背景、理由和重新评估条件。
- 后续 AI 协作容易只看到结论，看不到取舍过程。

为什么没有选择：

本项目要求重要决策可追溯，索引只应保存摘要。

### 方案 B：保持现状，不定义边界

为什么没有选择：文档与实现会继续背离，每次新增 continuation 能力都要重新争论产品定位，也无法阻止业务策略继续进入产品合同。

### 方案 C：一次性拆成两个 PyPI 包或立即降级 continuation

为什么没有选择：影响面过大，会与当前稳定化版本混合；边界尚未固化前拆包容易拆错，且 continuation 是当前真实高频使用路径，立即迁移会中断 dogfooding。

---

## 后果

### 正面影响

- 产品定位可被引用、可被审阅，并可被后续 ADR 与文档引用。
- 后续重构有明确验收方向：Core 不依赖 Operations。
- 新能力先判断属于哪一层，避免把业务策略继续塞进 Operations。

### 负面影响或代价

- 需要在本文件与 `reference/ACF_Top_Level_Design.md` 之间保持一致性。
- 部分命令横跨两层语义（例如 `acf log issue` 属于 Operations 的用户级台账），必须在文档中显式说明归属。

---

## 适用范围

适用于：

- ACF 核心产品分层判断。
- runtime 解耦的方向与验收条件。
- 新命令、新合同字段的层级归属判断。

不适用于：

- 通用模板使用者的强制流程。
- 具体实现步骤与排期（由后续独立 Workstream 承担）。

---

## 重新评估条件

1. Operations 被真正独立打包或整体关闭。
2. continuation 出现与 Core 的直接耦合，违反硬约束 1。
3. 多 agent / 多 Workstream UX 计划需要重新划层。
4. 该决策带来的维护成本超过收益。
