ADR：将 acf 演进为可安装的 AI-facing 上下文维护 CLI

## 状态

Active

---

## 日期

2026-04-27

---

## 背景

当前 acf.py 已覆盖 init、simplify、check、new task、new source、new worklog、new adr 和 writeback draft，但仍需要通过 uv run python acf.py 并显式传入上下文路径。为了让 AI 在任意项目子目录中可靠维护上下文，需要把 CLI 设计为上下文文件 API，而不是自由文本编辑器。

---

## 问题

当前 `acf.py` 已证明确定性维护命令有效，但它仍有几个长期缺口：

1. 主要调用方式仍是 `uv run python acf.py ...`，不适合外部项目或任意子目录使用。
2. 多数命令需要显式传入上下文目录，AI 容易在深层目录中传错路径。
3. 输出以人类阅读为主，缺少稳定的机器可读结果。
4. 还没有面向 AI 的安全结构化编辑原语，AI 仍可能直接手工改整份 Markdown。
5. 如果扩展过度，CLI 可能滑向通用 Markdown 编辑器、常驻 runtime 或语义判断系统，偏离项目边界。

---

## 决策

将 acf 从仓库内脚本逐步演进为可安装命令，支持自动发现上下文、机器可读输出、安全结构化编辑和写后检查；语义判断仍由人或 AI 完成，CLI 只负责确定性落盘和校验。

---

## 理由

1. AI 在真实项目中经常位于任意子目录；自动发现上下文比反复传路径更可靠。
2. 机器可读输出、dry-run 和写后检查可以降低 AI 误判命令结果的概率。
3. section 和 table 级编辑可以减少整文件重写造成的断链、索引遗漏和事实漂移。
4. CLI 只做确定性文件操作，能继续保持模型无关、纯 Markdown、人工可审阅的设计边界。
5. 语义判断适合由人、主代理或 subagent 完成，CLI 不应自行裁决事实。

---

## 考虑过的替代方案

### 方案 A：保持仓库内脚本形态

优点：

- 当前实现简单。
- 不需要调整安装和入口配置。

缺点：

- 外部项目和任意目录使用体验差。
- AI 需要知道脚本位置和上下文路径，容易出错。

为什么没有选择：

本项目的长期目标包括降低 AI 协作维护成本，仓库内脚本不足以支撑跨项目使用。

### 方案 B：做成通用 Markdown 编辑器

优点：

- 表面上适用范围更广。
- 可编辑更多文档形态。

缺点：

- 维护范围过大。
- 容易绕开上下文结构约束。
- 难以通过项目级 check 保证事实源一致性。

为什么没有选择：

本项目需要的是上下文治理工具，不是自由文本编辑器。

### 方案 C：内置 LLM 或常驻 runtime

优点：

- 可以提供更强的语义自动化。
- 可能减少人工分类步骤。

缺点：

- 破坏模型无关性。
- 增加部署、调试和迁移成本。
- 容易让自动化静默改写权威上下文。

为什么没有选择：

现阶段应坚持纯 Markdown 和确定性 CLI，语义判断通过草案和 subagent 辅助完成。

---

## 后果

### 正面影响

- 后续 CLI 规划有明确阶段边界。
- AI 使用场景成为一等约束，而不是人类 CLI 的附属体验。
- 可把重复维护动作逐步产品化，减少直接手改 Markdown。

### 负面影响或代价

- 可安装命令、上下文发现和结构化编辑会增加 CLI 复杂度。
- 需要更严格的测试覆盖路径安全、dry-run、JSON 输出和写后检查。
- 如果边界控制不好，容易扩大成通用编辑器或运行时。

---

## 适用范围

适用于：

- 本仓库当前 dogfooding 和 CLI 维护流程。
- 后续面向真实项目的 `acf` CLI 产品设计。

不适用于：

- 通用模板使用者的强制流程。
- 内置模型、常驻服务或私有存储方案。

---

## 重新评估条件

1. 任意目录调用在真实项目中不能显著降低 AI 维护错误率。
2. 可安装 CLI 或结构化编辑带来的维护成本超过收益。
3. 用户更需要的是库 API、编辑器插件或其他形态，而不是命令行工具。
4. 项目边界变化，决定引入运行时、数据库或模型相关能力。
