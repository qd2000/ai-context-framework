# ADR-0005 - 使用可选 Workstream 层管理并行目标线

## 状态

Active

---

## 日期

2026-04-30

---

## 背景

当前 `active/Task_Plan.md` 和 `active/Current_Task.md` 适合单主线任务，但多个 agents 并行处理不同目标时，需要独立 owner、边界、输出物、合并请求和证据落点。

---

## 决策

引入可选 Workstream 层，用于表达并行目标线。

Workstream 是协作协议，不是 agent runtime、调度器、线程、权限系统或安全沙箱。

默认单线项目仍使用 `Task_Plan` / `Current_Task`。只有存在并行目标线、独立 owner、独立写入边界或独立合并审查时，才启用 Workstream。

---

## 关键取舍

1. 默认不启用，避免单线项目增加噪音。
2. `ReadyToMerge` 与 `Done` 分离，避免“子线完成”被误认为“权威上下文已更新”。
3. 写入范围是协作契约，用于 check 和人工审查，不是权限隔离。
4. 子 agent 默认写 workstream、draft 或 assigned 文件，不静默写权威上下文。
5. front matter 只作为状态型详情文件的机器可读 metadata，不全仓库迁移。

---

## 不采用的方案

1. 不做常驻 agent runtime。
2. 不做调度器。
3. 不引入数据库、向量库或私有状态格式。
4. 不把 Workstream 替代 `Task_Plan`。
5. 不默认让旧项目生成 Workstream 结构。

---

## 后果

### 正面

1. 多 agent 并行时边界更清楚。
2. 合并前后状态更可审查。
3. check 可以发现明显写入冲突。
4. 旧项目和单线项目保持轻量。

### 代价

1. 增加一层可选结构。
2. 需要维护索引、详情文件和归档规则。
3. 需要 CLI/check 支持 metadata、状态转换和 scope claim。

---

## 重新评估条件

1. 后续使用发现 Workstream 给单线项目带来默认读取噪音。
2. CLI/check 实现成本明显超过并行协作收益。
3. Workstream 被误用为权限系统或调度器。
4. ReadyToMerge 与 Done 分离在实践中无法降低合并风险。
