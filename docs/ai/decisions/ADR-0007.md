ADR：ACF runtime 组合契约（显式导出、RuntimeContext 与命令树组合）

## 状态

Active

---

## 日期

2026-09-19

---

## 背景

ADR-0006 已判定 continuation / worktree / closeout authorization / usage log / execution-effect-recovery 属于可选 ACF Operations 控制面，并明确把「export allowlist → 显式 RuntimeContext → parser composition → 收敛 `acf.py` shim」列为后续独立 Workstream 的解耦方向。该解耦已在 WS016 执行完毕，需要把这套组合契约固化为可引用、可审阅的决策，而不是只留实现细节。

解耦前的实际形态：`ai_context_framework/runtime.py` 与 8 个 `runtime_parts/*` 模块通过 `__dict__` 双向合并共享全局（runtime 把自身顶层名字推给 parts，parts 把自己的名字推回 runtime）；`commands/workstream.py` 用 28 处 per-call `_bind` 复制符号；`runtime.build_parser()` 内联构造全部命令组；顶层 `acf.py` shim 通过写 `runtime.ROOT` 并调用私有 `_sync_runtime_part_globals()` 让 ROOT 变更生效。

---

## 问题

1. 双向全局合并让「谁定义了哪个名字、谁依赖了哪个名字」不可枚举：任何一处改名或删除都可能在运行时静默降级为 `NameError`，静态检索无法给出可靠影响面。
2. per-call `_bind` 在每个命令调用里重复复制符号字典，既掩盖真实依赖，也让 handler 的实际绑定对象（deps 适配器）与命令模块同名函数难以区分。
3. `build_parser()` 同时承担「命令组定义」与「命令树组合」，使 runtime.py 逼近 2000 行可审阅门禁，新命令必须改中心文件。
4. 顶层 shim 写 runtime 私有全局并调用私有同步函数，把「重绑定 ROOT」变成约定而非受支持入口。
5. 命令树形状（子命令、参数、dest、default、choices、handler）没有任何自动护栏，重构期间的外观漂移只能靠人工比对。

---

## 决策

采用显式组合契约取代隐式全局注入：每个 `runtime_parts/*` 模块用 `__acf_exports__` 显式声明导出并由安装期 fail-closed 校验；消费者改用显式 RuntimeContext；`build_parser()` 只做组合，命令组由所属模块的 `register_*_parser()` 注册且 handler 必须显式注入；`runtime.set_root(root)` 是唯一受支持的 ROOT 重绑定入口；命令树形状与导出面分别由快照护栏与审计脚本断言。

各条契约的准确边界如下：

1. **导出表 fail-closed**：每个 `runtime_parts/*` 模块用 `__acf_exports__` 显式声明它向 runtime 提供的名字；安装时按表注入，未声明即拒绝、声明缺失即拒绝、同名不同对象即拒绝。
2. **显式 RuntimeContext**：消费者不再 per-call 复制符号，而是接收一个 frozen 的 RuntimeContext（或在导入期显式接收依赖）。
3. **命令树组合**：`build_parser()` 只做组合，每个命令组由所属模块的 `register_*_parser()` 注册；超过可审阅规模的命令组使用独立 `*_parsers` 模块。
4. **handler 显式注入**：`register_*_parser()` 必须显式接收 handler。CLI 绑定的是 `runtime_parts` 的 deps 适配器，而不是命令模块里的同名函数，二者不可互换。
5. **受支持的 ROOT 重绑定**：`runtime.set_root(root)` 是唯一入口；`acf.py` 只在 `acf.ROOT` 与 `runtime.ROOT` 实际不同时调用它，不再写私有全局。
6. **契约护栏**：`tests/test_cli_surface_snapshot.py` 以 210 条路径快照锁定命令树形状（子命令、参数名、dest、nargs、default、choices、handler 限定名）；`scripts/runtime_export_audit.py` 断言导出表、消费者注入与动态访问均无缺口。

---

## 理由

1. 隐式全局注入的危害不是风格问题而是可审计性问题：它让「改名」这件事失去编译期与静态分析的护栏。显式导出表把这种漂移变成安装期 fail-closed 错误。
2. 命令组下移让 runtime.py 回到「只读的组合入口」职责，同时把新命令的改动面限制在单个命令模块。
3. handler 归属是这套重构中最容易出错的一处：若 `register_*_parser()` 直接引用命令模块的同名函数，命令仍能解析，但会因为缺少 deps 而在运行时出错。把它固化为显式注入 + 快照断言，才能让错误在测试期暴露。
4. ROOT 重绑定是唯一需要跨模块传播的可变全局；给它一个公开、幂等的入口，比让 shim 直接写内部变量更诚实，也不会随内部重命名而失效。

---

## 考虑过的替代方案

### 方案 A：保留双向 `__dict__` 合并，只补文档说明

为什么没有选择：文档无法阻止静默漂移，且每次新增 part 导出都会扩大不可枚举面；这与他人的既有审计诉求直接冲突。

### 方案 B：只做导出 allowlist，保留内联 `build_parser`

为什么没有选择：能解决注入面不可枚举，但中心文件仍会继续膨胀，且命令树形状仍无护栏。两者是独立收益，应一起做。

### 方案 C：把 handler 也纳入导出表自动绑定

为什么没有选择：会重新引入隐式绑定，且无法解决「CLI 绑定的是 deps 适配器而非命令函数」这一真实语义差异；显式注入让这层差异在代码里可见。

### 方案 D：让命令模块 import runtime 以取得 helper

为什么没有选择：runtime 会 import 命令模块，形成循环依赖。共享 helper 改为叶子模块（`ai_context_framework/cli_arguments.py`）与常量（`ai_context_framework/constants.py`），这是无环且可静态分析的形态。

---

## 后果

### 正面影响

- 注入面可枚举、可断言：导出表与消费者需求不一致会在安装期与测试期直接失败。
- `runtime.py` 从 1988 行降到 838 行，成为纯组合入口；命令组改动面收敛到各自模块。
- 命令树形状变化必须显式更新快照，重构期间的外观漂移无法悄悄进入。
- ROOT 重绑定成为受支持入口，shim 不再依赖 runtime 私有实现细节。
- CLI 命令、参数、JSON、退出码与 help 文本保持完全不变（快照零漂移为证）。

### 负面影响或代价

- 新增一个 part 导出、一个新模块或一个新共享 helper 时，需要在更多位置登记（导出表、`*_parsers` 模块、审计断言、必要时的快照更新）。
- 命令组分散到多个模块后，定位「某命令在哪里注册」需要按模块命名而不是单一文件。
- 快照断言是文本级契约：任何 help 文案调整都要同步更新快照，属于预期成本。

---

## 适用范围

适用于：

- ACF CLI 的 runtime / runtime_parts / commands 之间的依赖组织方式。
- 新增命令组、part 导出或共享 helper 时的落点判断。
- 命令树对外契约的变更审查。

不适用于：

- 通用模板使用者的项目结构（template 不含 runtime_parts）。
- ACF Core 与 Operations 的层级归属判断（见 ADR-0006）。
- 具体版本发布与 PyPI 流程。

---

## 重新评估条件

1. 命令模块数量增长到「按模块命名的 `*_parsers` 规则」不再可预测时。
2. 出现必须让 runtime 反向依赖某个命令模块的真实需求。
3. 快照断言带来的维护成本持续超过它捕获的漂移收益。
4. Operations 被真正独立打包，导致 runtime 组合范围显著变化。
