### v1.2 核心产品判断

Observer 不再要求所有任务套用同一种 generic roadmap/card 页面。每次 Production Observer semantic/Map Review 必须先从 fresh target authority 判断一个 `primary_progress_question`，再由 Agent 选择最适合回答该问题的主可视化；**ACF 只负责结构校验、来源/并发/历史约束和确定性渲染，不自行猜项目事实，也不得按 project/target 名称硬编码选择逻辑。**

首批通用 archetype 限定为：

- `metric_trend`：优化、误差、目标函数等可比数值随 iteration/time/generation/sample 的变化；有限值、方向、口径与 evidence 必须可验证，invalid/missing/sentinel 不补零；
- `status_matrix`：可枚举组件/模块/对象的完成、当前、阻塞、等待、未开始状态，当前元素突出并可进入同页详情；
- `process_flow`：工程流程、建模流程或数据处理流程，节点/边/方向必须来自 authority，当前步骤与阻塞位置突出；
- compact `roadmap`：真正以阶段/依赖/分支里程碑推进为核心的任务；只显示必要阶段和真实关系，不退化成长卡片列表。

`primary_visualization` 采用最小结构化合同：`schema_version / kind / title / primary_progress_question / reason / evidence_refs / spec`。Agent 的选择还应记录 `kind / primary_progress_question / reason / evidence_refs / confidence`；`confidence=low` 时页面 fail-visible 表示低置信，而不是伪装权威。缺少可靠 specialized spec 时允许 generic fallback，但 fallback 不能被误报为已经完成 task-semantic visualization。

### v1.2 页面与 dogfood 目标

每个 target 默认只保留 **一个 dominant primary visualization**。主图应明显高于 provenance、raw ID、schema 与完整 run technical details 的视觉优先级；最近 3—6 条可归属 run 可用紧凑 strip/table 展示，完整 run history、历史可视化、架构/次级视图和原始证据进入二级区域或折叠层。页面继续中文优先、single-file/self-contained、`file://` safe，仅使用 HTML/CSS/inline SVG/native JS；JS 不可用时仍须有可读 fallback。

真实 dogfood 的预期 archetype 只作为**基于当前 authority 的验证假设**，不得硬编码：WS086 优先验证 `metric_trend`（obj 的 current/best/events），WS079 优先验证 `status_matrix`（组件状态矩阵），WS080 优先验证 `process_flow`（当前真实 FCC/建模过程），WS012 优先验证 compact `roadmap`。若 fresh authority/evidence 证明更适合其他 archetype，Agent 可以改变选择，但必须记录理由与来源。

历史 visualization 保存 structured spec + source/evidence identity。相同 kind 可以比较结构差异；kind 改变时必须明确显示“可视化类型已改变”，不得伪装成可直接等价的连续 A/B 图。current 永远优先，archive 不反向覆盖 current。

### v1.2 H1 执行与关闭条件

H1 当前保持 open。执行顺序更新为：先冻结 generic renderer 为 fallback → 建立最小 `primary_visualization` contract → 依真实目标实现/验证 `metric_trend`、`status_matrix`、`process_flow`、compact `roadmap` → 生成 fresh real ACF + FCC candidate dashboards → 用户人工视觉复核。新的人工 **PASS** 前不得关闭 H1，也不得正式进入 H2。

## 1. 已确认的需求与产品边界

### 1.1 用户真正要看到的结果

页面的核心价值是展示**进展和进度**，项目地图是实现这一目标的主要方式，而不是替代进展汇报的理由。应同时回答三个尺度的问题：

- **整体尺度：**最终要实现什么，主要路线是什么，哪些部分完成、进行中、未开始或受阻，距离完成还缺什么。
- **阶段尺度：**当前在哪里，为什么做这一步，最近证明或排除了什么，问题影响哪里，下一步是什么。
- **执行尺度：**每次实际运行分别做了什么、得到什么结果、有没有改变阶段/指标/计划，有无完整结束证据；没有进展或记录不足也如实展示。

以上信息相互关联：运行结果可以关联路线节点、问题和指标，但不要求每次运行都新增一个主图节点或产生正向进展。

“有 HTML 文件”“文字变成中文”“卡片之间插入箭头字符”“测试通过”都不能单独证明可视化目标已实现。

### 1.2 已确认的功能要求

| 要求 | 必须保持的含义 |
|---|---|
| 地图服务进展 | 图为主体，保留清楚的进展摘要、阶段成果和下一步；不能把“不是日志页”误解成“不展示运行成果”。 |
| 分层但可追溯 | 默认完整主线和主要阶段，细步骤按需展开；每次实际运行的结果另有可检索记录，不能被阶段汇总吞掉。 |
| 路线与架构分开 | 推进路线说明先后、分支和依赖；架构视图说明模块关系或数据流。可联动，不混用含义。 |
| 当前优先、旧图归档 | 当前页优先当前有效版本；失效或被替代的旧图进入可查看的历史档案，不继续充当当前主图。 |
| 历史可查看、可对比 | 用户可选择已有历史版本查看或比较；默认不叠加全部旧路线。历史证据不足的部分明确不可用。 |
| 灵活数值图表 | 纳入本轮能力范围；Agent 按目标和证据判断是否展示、展示什么，人也可指定。不能要求所有任务都有同一组指标。 |
| 中文优先 | 主标题、状态、说明、问题、运行结果使用中文；技术标识保留在次要层，不能用英文状态堆砌主视图。 |
| 北京时间 | 人类可见时间统一为北京时间；底层 UTC、排序和证据时间语义不改。 |
| 真正的关系图 | 实际图形连接节点，能看出方向、关系、当前位置和受影响位置；不是卡片加关系列表。 |
| 独立目标页面 | 只展示显式注册目标；目标间语义、运行记录、指标和告警不串线。 |
| 有条件的项目总图 | 只有证据支持统一目标或架构时才启用统一 Project Overview；任务摘要不等于统一逻辑路线。 |

### 1.3 保持现有工程与安全边界

继续采用自包含 HTML/CSS/inline SVG 和 `file://`，不增加 React、Mermaid/Graphviz 运行时、CDN、HTTP daemon 或第三方运行依赖。Observer 保持 **read broad / write narrow / control none**，只在用户级派生目录保存观测、展示和历史，不取得 Writer ownership，不改项目 Git、权威计划或外部控制状态。

重要成果、原因、问题影响不能被技术细节折叠规则一并隐藏。缺失预期目标、没有有效数据、语义陈旧或记录不完整，不能用绿色“健康”掩盖。

实际浏览器检查和语义对照不可由测试数量代替；用户视觉反馈可推翻 machine-only PASS。阶段、commit、截图或一次 release 是检查点，不是 Agent 固定工作配额、时长限制或长期任务结束条件。[S03—S06]

| Q3 | 分开。 | 推进路线和系统架构采用独立视图，可按稳定引用联动。 | 两种箭头含义不混淆；无架构依据时说明，不编造。 |
| Q4 | 旧图可以保留，但是需要归档。 | 旧图成为持久、可访问、有版本与来源的历史档案；失效后不再显示为当前主图。 | 当前区与历史区明确分离，不只是加灰色样式或折叠旧图。 |
| Q5 | 优先展示当前，历史可以选择对比和查看。 | 默认当前路线与变更摘要；支持选择历史版本查看、选择版本比较。 | 版本时间、差异和来源可辨；不拿今天的图倒推过去。 |
| Q6 | 可以加入，视具体情况，灵活让 Agent 判断，也可以人为指定。 | 数值展示能力纳入本轮；选择、解释和图型由证据驱动，支持人工指定以及后续修改/撤销。 | 有用且有数据就展示，不适用就不强凑；不能伪造改善或进度百分比。 |

对 Q4 的明确解释：用户选择的是**保留并归档旧图**，不是“陈旧图一直留在当前页”。当前语义尚未完成复核时，应展示待复核状态、有来源的事实摘要和历史入口，而不是以历史版本顶替当前结果。

对 Q2 的明确解释：当前用户工作方式是每小时触发，但产品按真实运行身份归属，不把“一小时”硬编码为运行时长、执行配额、强制结束时间或所有目标的固定 cadence。

对 Q6 的明确解释：加入的是灵活能力与选择机制，不是要求每个任务固定出现折线图，也不是允许 Agent 随意推测数字。

## 4. 范围、优先级与明确不做的事项

### 4.1 必须交付

1. 真正的分层推进关系图，独立的架构视图，以及当前位置、阶段成果、问题影响与下一步说明。
2. **逐次运行成果记录**：每次有来源的运行均可查，最新记录突出，但不覆盖或吞并以往运行结果。
3. 当前与历史分离：旧图归档、版本选择查看、已有版本对比、缺失历史的诚实说明。
4. 灵活指标展示：有来源的当前值/变化/趋势，Agent 判断和人工指定都可生效；不适用时不强行展示。
5. 中文、新鲜度、真实运行状态、expected-target 完整性与有依据的恢复、持续语义复核、真实页面和安装态验收。

### 4.2 可按实际情况灵活决定

配色和间距、阶段展开深度、初始运行记录数量、图的排布方向、指标和图型、默认历史筛选范围等属于实现选择。它们可以改变**默认展示方式**，不能改变“每次结果可查”“旧图确实归档”“当前优先”“数据真实”的必达要求。

关键指标没有足够数据时，不阻塞路线图和缺项告警；但必须交付无数据状态和后续使用入口。已有适用的权威数据时，不能以“图表可选”为由长期不实现或不验证这条能力。

### 4.3 本轮不扩展成这些产品

不做通用图形编辑器、拖拽修改计划、浏览器改任务状态、调度控制台、跨项目统一指挥中心、常驻网页服务、完整 BI 平台、自动事实裁决器或独立前端技术栈。

不重建无法验证的全部旧历史，不强制将每次工具调用画成节点，不把全部原始日志搬进页面。不能手工美化一份正式 `dashboard.html` 后宣称修好了通用产品，也不能为了逐次成果展示另起一套 Writer 所有权/执行状态机。

## 5. 信息架构与默认阅读方式

### 5.0 2026-09-10 人工视觉复核 FAIL：H1 信息架构纠偏

用户已人工查看当前 ACF 与 FCC Dashboard 截图，并明确判定 **H1 MANUAL VISUAL REVIEW = FAIL**。该人工结论是一等 acceptance evidence，覆盖此前任何仅由 machine tests、SVG 存在、HTML 生成成功或截图生成成功形成的“接近通过”判断；在新的人工 PASS 之前，H1 必须保持 open。

下一轮 H1 工作优先级由“继续补底层展示字段”切换为**视觉信息架构重构**，并冻结以下验收要求：

1. **真正 map-first**：主视图不能继续表现为长文档或纵向大卡片列表。完整路线要压缩为一眼可理解的阶段 / 分支 / 当前路径图，路线图本身成为首要视觉主体。
2. **进度首屏突出**：常见桌面视口首屏或一屏半内必须直接看出已完成、当前、下一步、剩余阶段与最近实质进展；关键进度不得埋在长段解释中。
3. **路线图与架构图分离**：二者用独立切换 / 入口呈现，不在同一长页面连续堆放两套图义。
4. **中文主展示**：FCC 等真实项目中的英文技术长段落不得直接占据主区；主区保留中文解释，英文技术原文进入可折叠技术详情。未知值仍 fail-visible，不得伪造翻译或语义。
5. **大幅去重**：当前位置、为什么现在做、下一步、当前执行范围等语义只能各有一个权威主展示；重复内容移入折叠详情或通过引用联动，不再多处复述。
6. **Agent run 降级为紧凑辅区**：每次 run 仍须可查，但默认以紧凑时间线 / 表格展示时间、时长、结果、主要产出与路线关联；完整历史按需展开，不能抢占项目地图主体。
7. **stale / not-reviewed 不退化成长原文页**：FCC target narrative 未复核时只显示紧凑 fail-visible 提示；若存在历史有效图，必须提供归档 / 历史入口，而不是把原始执行文本抬回主区。
8. **视觉层级明确**：当前节点、问题、下一步、最近进展高于 provenance、ID、schema、raw evidence；技术 provenance 默认折叠。
9. **控制纵向长度**：计划节点、历史、运行详情和技术详情采用分层 / 折叠 / 切换；目标是在常见桌面分辨率首屏或一屏半内理解总体目标、完整路线、当前位置、最近进展、问题与下一步。
10. **真实 ACF + FCC 页面再验收**：完成本轮信息架构重构后生成新的 ACF 与 FCC 实际 Dashboard，保留 H1 open 并等待新的人工视觉复核；不得因本反馈另起 Workstream、修改 scheduler 或重开 continuation P0。

实现顺序以“首屏地图骨架 → 紧凑进度 / 当前 / 下一步 → route / architecture 切换 → run/history/details 降级 → stale fail-visible → 真实 ACF + FCC render”为优先。只有能直接改善上述人工 FAIL 的底层改动才可插入本轮 H1 主线。

### 5.1 项目入口

保留现有每项目 canonical Dashboard 与快捷方式。单目标项目优先直接进入目标内容；多目标项目提供简短的任务索引、每个目标的进展摘要、最新运行结果和告警，再进入独立目标页。目标切换不能悄悄改变所查看历史或指标的归属。

“任务索引/进展摘要”与“统一项目路线图”是不同能力：前者只汇总注册目标，后者必须有 authority 支持。FCC 不因存在三个任务就被强行连成一条线；统一 Project Overview 不适用时，也不能使三个任务的进展概览消失。

### 5.2 目标页的阅读顺序

| 区域 | 默认可见内容 | 可继续展开或选择的内容 |
|---|---|---|
| 目标与进展摘要 | 最终目标、已完成的关键部分、当前位置、尚缺事项、是否需人工介入。 | 验收边界、完整依据；有明确统计口径时的进度数字。 |
| 当前推进路线 | 完整主线、主要分支/并行关系、当前路径、问题标记及近期发生变化的节点。 | 阶段内步骤、节点详情、关联运行结果。 |
| 系统架构视图 | 独立入口，说明模块或数据流关系；不是路线图的混合箭头层。 | 模块详情、依赖与证据；无依据时给出说明。 |
| 当前决策与成果 | 为什么现在做、最近证明/排除/改变、下一步及理由。 | 支撑证据、关键条件与不确定性。 |
| 最新运行结果 | 最近一次实际运行的成果、状态、起止/最后活动时间；若仍进行中则明确标识。 | 本轮多项成果、相关问题、指标变化、与路线的关联。 |
| 每次运行记录 | 按时间排列的多次运行摘要，显示当前筛选范围及记录覆盖情况。 | 日期/运行选择、更多历史、单次详情及原始证据引用。 |
| 关键数值 | 适用时展示当前值、同口径变化及简明趋势；不适用不留装饰空图。 | 指标选择、口径、数据范围、单点证据；接受人工配置。 |
| 当前问题与影响 | 阻塞/影响范围、处理者、下一动作；优先重要问题。 | 已解决问题、转交信息、调查历史。 |
| 历史与对比 | 默认收起的明确入口，以及最近路线变化摘要。 | 已归档版本选择、单版本查看、版本对比。 |
| 技术详情 | 清晰的折叠入口。 | HEAD、generation、fingerprint、schema、原始 provenance 等。 |

“首屏看懂”不是把所有字段挤在一个视口里。首先看到目标、整体进展、当前图与近期成果；逐次成果区和历史入口应容易发现，不能藏在 raw technical details 中。

### 5.3 地图和运行记录联动

主图回答“整体推进到哪里”，逐次记录回答“每次执行贡献了什么”。点击节点可看其关联运行和证明；点击运行可定位本轮涉及的节点、问题或指标。一次运行涉及多个节点时全部按证据关联，不强选一个；证据不足时明确“尚未定位到具体节点”。

同一成果不得因被主图、摘要和运行记录引用而计算成三次进展。运行结果是独立记录，阶段汇总是引用与解释，不相互覆盖。

### 5.4 视觉风格和布局

采用浅色、工程文档式界面作为初始方案，减少装饰性大卡片和过多空白，给图与成果内容足够宽度。中文自然换行；关键说明不只通过 hover 提供。状态用文字及形状/线型配合颜色表达。

主要检查 `1920×1080`、`1366×768` 桌面视口、常见缩放和较窄窗口；这些是测试场景，不是产品尺寸限制或 Agent 工作指标。布局可根据真实信息密度调整，不要求用户重新确认每个间距。

## 6. 图形语义与交互规则

### 6.1 路线图承载阶段进度，运行记录承载逐次成果

路线节点优先代表对最终目标有意义的阶段、能力、验证结论或决策点；普通 heartbeat、工具调用或 commit 不自动成为主图节点。**这条降噪规则不适用于删除逐次运行结果。** 即使某轮只排除了一个失败方案，也应在该轮记录中说明，并在有必要时关联到相应节点。

节点完成必须有对应验收或证据。一次版本发布或局部修复不自动使长期 maintenance mission 完成。已完成阶段保留成果和证据；不再有效的旧路线进入历史，而不是和当前路线并列表示当前计划。

### 6.2 分层不等于裁掉剩余计划

默认展示完整主线与重要分支，允许展开阶段内部细节。当前阶段可默认展开更多；已完成阶段默认保留结论，不必铺开全部实验。布局不能通过省略未完成阶段营造“接近完成”。

折叠后的跨层关系应可解释：隐藏步骤所属阶段可作为可追踪的汇总端点，但须能展开查看真实端点，不能发明新的实际依赖。展开/折叠只改变显示，不改变节点完成状态和计划含义。

### 6.3 路线与架构分别表达

推进路线中区分顺序、前置依赖、并行汇合、条件分支和真实反馈循环。架构视图中区分模块关系、接口或数据流。不能因数组相邻而补依赖边，也不能用同一种未解释箭头混合两类视图。

优先实现真实样例需要的分层路线、并行分组、架构关系布局，不先开发通用图论引擎。已有其他 `presentation_type` 需要明确兼容展示或诚实的能力说明，不能忽略边后仍报告图形验收成功。

### 6.4 当前状态、近期变化与图形位置

当前位置绑定稳定节点身份，支持有证据的多个并行位置；下一步指向已存在节点，或明确尚待决策。节点的完成状态、Agent 是否运行、数据是否陈旧、问题是否阻塞是不同维度，不能合并成一个红绿灯。

允许突出近期完成、正在推进或新受影响的节点，并说明突出基于哪次观测或运行。不得把“看起来活跃”的动画当作执行证据，也不能用新状态重新涂改旧图。

### 6.5 最小交互

点击节点看目标、成果、状态依据、问题和关联运行；阶段展开/收起；定位当前位置、查看全图；切换路线/架构；打开某轮结果；选择历史版本查看/对比；适用时选择指标。

交互只改变查看方式，不改计划、不触发计算、不执行外部命令。浏览器 JS 仅为渐进增强；关键图文不能因脚本失败而空白，历史入口和基本阅读也应有非脚本退化方式。

## 7. 数据契约：优先复用，按需最小扩展

### 7.1 保持现有责任分工

项目 Markdown、计划、Workstream、正式 directive 和可核验 evidence 是依据。Observer Agent 阅读并形成有来源的语义解释；ACF 校验结构、身份、引用、并发与新鲜度，再确定性地投影和渲染。浏览器只显示派生产物。

不能要求 CLI 自行理解任意 Markdown 并决定“哪条路线是真的”“哪个实验已经完成”。也不能新增由人手工维护、但会与原计划漂移的第二份路线事实。

### 7.2 可复用字段

现有 `route_nodes`、`route_edges`、`overall_goal`、`route_summary`、`current_position`、`why_now`、`recent_proof`、`next_logic`、`evidence_refs` 为主要输入；问题继续复用 `problem_id/node_ref/route_ref/handler/blocking_impact/plan_impact/status/evidence_refs` 等。

现有校验器会构造规范化字段集合，不能认为向 payload 随意多塞字段就一定会被保留。新增字段必须同时进入校验、读写、projection、CLI 合同、测试和文档。

### 7.3 候选最小扩展（不是现成字段或已有 API）

| 需求 | 候选表达 | 约束 |
|---|---|---|
| 准确定位当前/下一步 | 显式当前节点与下一节点引用集合。 | 只引用已存在节点；旧记录缺失时明确“不具备节点级定位”，不瞎猜。 |
| 主线与细节分层 | 可选父节点、分组或泳道标识。 | 仅为实际需要分层的目标提供，不要求所有目标填满。 |
| 关系可解释 | 可选关系类型、边证据；必要时增加稳定边身份。 | 不从一个含糊的文字 label 自动裁定语义。 |
| 验收与成果可读 | 引用现有验收条件/成果来源，必要时增加简短派生摘要。 | 不复制维护完整项目规范。 |
| 逐次运行结果 | 现有运行身份引用、成果摘要、阶段/问题/指标引用、证据覆盖说明。 | 优先补 Observer 派生解释；不新建 Writer 执行账本，不把 observer render 当 Writer run。 |
| 归档与版本对比 | 目标身份、语义版本、图内容/来源、归档原因与时间、前后版本引用。 | 复用已有版本历史；旧版本保留自己的事实，不读当前状态补旧图。 |
| 灵活数值展示 | 指标身份、单位、可比数据集/版本、样本来源、展示选择与人工规则引用。 | 已纳入范围但按适用性启用；不得强迫所有目标提供同一组指标。 |

先证明现有数据无法正确表达具体真实场景，再添加对应字段。不要为可能用到的功能一次性扩展整个 schema。

### 7.4 兼容性与校验

旧 registry 和旧 semantic review 必须可读取。新增可选字段缺省时提供诚实退化，不静默改变旧事实含义；未知状态有可读说明，不把不认识的值映射为“完成”。若确需 schema 版本升级，应给出非破坏性迁移和回滚方案。

校验至少覆盖重复节点、不存在的端点、错误当前节点、问题引用悬空、父子循环、不同目标之间的误引用。关系图中的合法反馈循环不应被统一当成坏输入；层级父子循环与业务反馈边需要分开处理。

### 7.5 四类派生对象彼此引用，不互相充当事实源

路线/架构语义、逐次运行成果、历史版本、指标序列属于不同派生视角。它们共享稳定 target 身份，并通过来源和可验证引用关联。运行报告不反向覆盖 continuation 的真实起止/状态；指标展示选择不改指标定义；历史对比不反向修改今天的计划。

运行摘要晚于执行结束才生成时，单独保留摘要生成/复核时间，不能据此补写执行结束。字段扩展应能表达“不知道”“尚未归属”“历史不足”，避免为了通过必填校验诱导 Agent 编造结果。

指标或逐次结果来源改变，不应无理由使无关 target 失效；仅影响展示的筛选和密度改变也不能制造新的语义路线版本。

### 7.6 稳定身份与历史保真

同一 target、同一视图中的同一语义节点尽量沿用既有稳定身份；标题、布局坐标、review 时间戳不能充当身份。拆分、合并或替换只有在有来源时建立显式映射；没有映射就展示新增/移除并说明无法精确对齐，不按标题相似度推断。路线与架构使用明确命名空间，跨视图联动需要显式引用。

历史 HTML 是可重渲染的，但历史语义与当时的成果说明未必能从当前文件重建。至少保留每个语义版本的规范化内容、来源时点/指纹与可核验引用；后续事实修正另记更正及其适用范围，不静默改写“当时是怎么判断的”。不为此复制整个仓库或全部原始日志。

## 8. 确定性渲染实现建议

新增小而纯的图形布局/渲染模块，由现有 Dashboard 渲染入口调用；不要把所有新逻辑继续堆入长 HTML 字符串，也不要借机大改全部 Observer 存储系统。

建议流程：校验后的语义输入 → 非持久化统一图形投影 → 确定性布局 → inline SVG 与可访问文字详情 → 既有 Dashboard 外壳。相同输入、同一渲染版本下，节点位置和输出应稳定，避免每轮刷新随机换位。

应处理中文换行、长标题、长路径、跨层连线、分支标签、箭头遮挡、多个并行当前位置及问题标记。过大的图采用分组/展开/缩放，不把所有文字缩成无法阅读的小字。

浏览器端不从本地 sibling 文件 `fetch` 数据，不依赖外网字体或脚本；必需数据随单文件内嵌。HTML/SVG/JSON 均须安全转义，不允许把来自 narrative 或 evidence 的文本当作可执行 HTML/JS。证据路径默认作为安全引用或复制入口，不自动执行 `file:`、shell 或不可信 URI。

生成采用现有原子写入与 last-good 保护；失败时保留已有可用产物并显式报告错误。失败产物不得覆盖正式好文件，也不得把旧页面时间改为现在掩盖失败。

### 8.1 单文件与历史归档的兼容方式

“单文件”约束是：主 Dashboard 本身以及用户打开的每一份历史展示，都不依赖 sibling JSON、外部脚本、字体或服务才能阅读；**并不禁止既有用户级 Observer runtime 保存历史文件**。

优先把常用历史版本与逐次摘要作为精简的已校验派生数据内嵌，浏览器只负责筛选/展开。历史很多时，可由同一正式生成链路输出按明确范围组织的独立、自包含历史 HTML，并在主页面提供受控入口；不得临时使用 `fetch(file://...)` 拼装数据或把未内嵌历史伪装成可选项。具体是否需要分卷，以实际历史规模为据，避免第一版先建复杂存储层。

最小实现选择：当前 Dashboard 内嵌当前图和近期成果；每个 target 的历史浏览器内嵌其可选择的精简、已校验图形语义版本，允许任选两版在该页本地比较；逐次运行长历史可独立按日期分卷。不要为 n 个版本预生成 n² 个比较文件，也不把全部原始运行日志塞进图形历史页。

若真实规模迫使图形历史也分卷，版本选择器必须说明当前可比较范围，并交付实际可用的跨卷查看/比较路径后才能声称“所有已保存版本可比较”；仅有跨文件链接不等于有比较能力。可选择受控加载本地归档导出数据，但仅解析校验过的惰性数据、不执行其中脚本；不是第一版必须增加的通用导入器。不能以尚未出现的大规模为由先建设复杂存储系统。

用户点击的历史导航只允许定位生成器在 Observer 命名空间内实际生成的安全文件；不得把任意 evidence 文本直接转成可执行 URI。浏览器查看旧版不修改其状态、不触发 snapshot 或新增 run。

### 8.2 失败保护与静态文件的诚实边界

若渲染失败，保留上次完整 HTML 及其原始时间，并在 Observer 状态/错误输出中报告失败；有能力安全生成错误外壳时可显示故障提示。不能承诺已经打开的静态旧页面会自动知道生产侧刚发生的新故障，也不能为了“看起来新”只改旧页面的时间戳。

上次文件被保留不等于其语义被重新认证为 current。正式验收同时看生成结果、runtime 状态和页面所示 as-of，不能只看文件存在。

### 8.3 局部失败与复杂度预算

一个 target 的语义、图形或指标无效时，隔离该部分并显示可定位的中文原因；其他已验证 target、逐次成果与安全正文仍可阅读。全局身份/安全问题仍按原合同拒绝，不能把 fail-visible 偷换成吞掉错误。主图失败不以伪造关系图兜底，可展示有来源的文字和证据入口，并保持对应视觉验收未通过。

历史渲染按不可变版本复用，运行历史按新增/修订身份增量处理；无新来源时不反复扫描全部历史或为每轮重建所有历史页面。性能验收记录代表性数据规模、HTML 体积、生成/打开耗时及浏览器可操作性；不把这些测试样例转成 Agent 工作时限或删历史阈值。

## 9. 新鲜度、当前视图与运行真值

### 9.1 分清四类时间

明确区分项目事实观察时间、语义复核时间、页面生成时间、目标最近执行/活动时间。页面刚生成不代表路线刚复核，浏览器刚打开不代表刚获取新事实；所有人类可见时间为北京时间，底层仍使用 canonical 时间。

页面是静态文件，查看新的生产产物依靠重新加载。可以说明“当前显示截至何时”，不宣称在后台持续采集。运行结束时间与 Observer 首次看到终态的时间也不能混同。

### 9.2 当前图与旧图状态处理

| 状态 | 当前页面 | 历史归档 |
|---|---|---|
| 首次未复核，且无旧图 | 显示有来源的目标/直接事实和“路线待建立”，说明缺项。 | 明确无可用历史，不造图。 |
| 当前语义有效 | 展示当前图、进度、成果及证据时间。 | 已归档旧版保留，默认不展开。 |
| 来源改变，旧语义失效 | 停止把旧图放在当前主图区域；展示待复核原因、直接事实与历史入口。 | 旧图作为上次有效解释归档，注明复核时点、失效原因及非当前结论。 |
| 新语义替代旧语义 | 当前区展示新图和变更摘要。 | 旧版归档并关联 successor；用户可选择比较。 |
| 只有展示样式变化 | 重渲染同一事实/语义版本，不伪造路线变化或进展。 | 需要时记录展示版本，不为每次样式/刷新制造语义历史。 |
| 归档或渲染失败 | 清楚暴露操作失败；不宣称迁移/刷新成功。 | 保留原版本和可恢复数据，不破坏唯一旧证据。 |

“归档”必须形成可检索的持久记录与来源关联，不是把旧图加灰、藏进一个未持久化的折叠区。历史入口展示的旧图有独立标题和日期，不与当前结果混放；细节见第 11 节。

**失败时分开处理事实有效性与文件持久性。** 已确认 source drift 后，即使归档/索引写入失败，旧版也不能继续被判断为 current；保留原始内容、报告 stale/归档失败并拒绝发布伪 current 版本。只读 `status`/`presentation-status` 可计算 stale，但不得因此落盘归档；正式授权的 Observer 写路径负责幂等物化历史。已经打开的静态页只能代表其生成时点，不声称能即时获知后端失败。

### 9.3 运行时间与状态

完整运行展示有依据的开始、结束、跨度和主要结果。未完整结束展示开始、最后活动和“未见结束记录”；根据证据区分“正在执行”与“结束情况未知”，不能把两者都翻译成活跃。

时长只能按已知起止或观测跨度/下界计算，并标明口径，不称为连续思考时间、有效工作时长或平台最大时限。heartbeat/stale timeout 不是结束时间；Observer 更新不增加 Writer 执行时长。

Writer、Production Observer 和 Maintenance verification 的记录分开标识；一次只读观测、重渲染或重复唤醒不能自动记为 Writer 取得成果。

### 9.4 防止“每次刷新都把图变旧”的版本混淆

把路线上决定性的变化、节点事实状态变化、运行成果补充、指标新样本、纯样式变化分别评估。新 run/heartbeat/generation/render 并不自动意味着路线改变；但含有路线、问题或验收变化的新证据必须触发必要 authority 重读。

保留现有 exact source fingerprint 与并发校验：不能通过忽略源变化或直接把 stale 改成 current 绕过复核。最小实现可以在 fresh source 上记录有 reason/evidence 的 unchanged 复核并延续同一语义内容版本；审计 review 次数与图形内容版本分开。只有事实影响确实分离且有回归保护后，才引入更细粒度 source projection，不要求先重构所有 fingerprint。

未完成复核期间仍按 9.2 标记待复核、提供已归档版本入口。验收应证明：同一路线经过多轮不同成果，记录逐条增加而路线版本不无意义膨胀；真正变更完成状态/依赖/验收/问题影响时，又不会被错误当作 unchanged。

## 10. expected-target 完整性与恢复

### 10.1 必须表达的状态

至少区分首次未配置、预期目标完整、部分预期目标缺失、registry 丢失/损坏、配置已明确撤销或故意为空。状态名应兼容现有 JSON 合同；中文显示必须明确，不能仅把它们都降为“无告警”。

没有可核验的观测范围和数据，不能显示绿色“健康”。同时避免把“尚未配置”夸张成“项目已失败”；页面应说明是观测缺口，而不是编造项目执行结论。

### 10.2 恢复依据

恢复只能依赖用户已经确认的 expected targets 与最新实际绑定，不能扫描所有 Workstream 后全部注册。FCC 的验收目标为 WS079、WS080、WS086，但实际 continuation task-id、automation identity、worktree 绑定必须现场读取，不能硬编码历史猜测。

优先复用现有明确、可审阅的持久配置。若没有适当位置，由用户/有权 Writer 维护一份明确的配置（可采用 Markdown），Observer 仅只读消费；位置在执行设计中基于项目入口确认，不假装本轮已存在这样的文件。

关键条件是：恢复依据不能只保存在可能一起丢失的 Observer 运行目录里。没有可用的明确依据时，只报告未配置/缺失及所需动作，不自动恢复。本文不声称能够在全部外部依据都丢失时恢复全部目标。

本轮向 WS012 下发计划不额外授予修改 FCC/AStockT_AI 项目文件、其他任务控制面或调度设置的权限。可在已有授权边界内读取并恢复用户级 targets；若需要新的项目级 expected 配置而缺少写授权，输出精确缺项/转交，不在别的项目偷偷建 authority，也不因此停止 ACF 渲染器和其他无冲突实现。

### 10.3 必测边界

重复恢复应幂等；部分缺项不改现有无关配置；registry 损坏不直接覆盖唯一原件；用户主动撤销的目标不能在下一次刷新复活；expected 配置和撤销记录冲突时应明确报告并要求权威配置统一，不新增一套不透明的“猜测优先级”。

将“任务目录总览”与统一项目路线决策分开。统一 Project Overview 的 enable/disable 均需中文理由与证据，不能为了省事禁用，也不能为了页面完整而强拼。

### 10.4 完整性、运行健康和解释新鲜度分开

分别表达“该观察的目标是否齐全”“已知执行是否存在问题”“路线解释是否最新”。某个任务正常，不足以覆盖另一个预期目标缺失；一个目标等待语义复核，也不能被误说成其计算任务已经失败。

明确故意不观察的目标和未经注册的 Workstream 不进入完成率、告警总数或运行成果。恢复后必须读取并核实 target scope，再进行语义复核；仅 target 数量恢复不代表路线图或逐次结果已经可用。

## 11. 每次运行成果、问题与历史归档

### 11.1 每次实际运行都可查

这是 Q2 的必达要求，不能退化成“最近一次运行 + 总体时间线”。按可验证的运行身份保留独立条目，至少能查看以下信息；没有证据的字段明确标记缺失，不编造填满。

| 信息 | 展示要求 |
|---|---|
| 归属 | 目标、Writer/Observer 身份、实际 run/round 身份及其口径。 |
| 时间与状态 | 开始、结束或最后活动；成功、失败、部分完成、等待、未完整结束等按证据说明。 |
| 本轮做了什么 | 任务意图/实际动作的可读摘要；两者不同要说明，不把计划当已执行。 |
| 本轮得到了什么 | 证明、排除、修改、交付、发现的问题、有效诊断结论；没有可验证增量就明确说。 |
| 对整体进度的影响 | 完成/推进了哪些阶段、哪些仍未通过、是否改变下一步；未跨里程碑也可有实质结果。 |
| 关联位置 | 相关路线节点、架构模块、问题、指标；无法确定归属时不猜。 |
| 本轮数值变化 | 有可比数据时显示前后值、单位和来源；没有则不强行生成。 |
| 下一步与需协助事项 | 依据本轮结果形成的建议/已确定行动及其状态，不冒充已批准计划。 |
| 证据与覆盖说明 | 可回到已有记录；区分完整摘要、部分可归属信息、仅发现启动或终态等。 |

每条摘要可包含多个结果，不能用一个“成功”标签覆盖失败分支和剩余问题。无需人为凑成果：重复唤醒后安全让出、授权等待、实验失败、排除无效路线，都应按其真实性质记录。

### 11.2 运行身份与“每小时”的边界

优先使用已存在的可验证 activation/run identity；没有外部 activation 身份时，按已记录的 continuation round 展示，并明确这是该口径，不保证一条就是一次整点触发。generation 变化、recover、snapshot 和每次 render 都不自动成为一次新的外部任务执行。

同一运行被多次观测时更新或补全该条成果，不重复计数；同一 activation 内有多个可确认执行片段时可分组，但不据相邻时间猜测归并。跨小时仍运行的同一次执行也不能被拆成两个伪造“小时成果”。

用户当前按小时查看，页面可按日期/小时组织已有记录。只有存在明确的预期调度依据时，才展示预期时段的记录覆盖情况；某时段没有记录，应写“未找到可归属执行记录”，不能直接断言 Scheduled Task 没触发，更不能补造成功的空运行。

优先复用现有 continuation history、effect/progress/evidence、外部已登记的 narrow run marker。若成果来源不足，补 Observer 的有来源派生摘要和缺失说明；不要为 UI 强迫所有 Writer 增加高频心跳或重构 continuation P0。

H0/H1 用真实样本建立最小来源表：运行身份来自哪里、动作/结果来自哪里、哪些证据可准确归属、哪些只有时间相关性。正式流程覆盖观测周期内新出现的所有可归属运行，而不只读取最新一条或最新 owner。若现有 Writer 缺少最低成果证据，可在其当前授权入口补简短 evidence 输出合同；不得先建设新执行账本，也不得假定所有项目马上都支持。

运行状态、成果摘要完整性与目标验收结论分开。命令 exit=0/程序完成不等于科学目标达到；只有启动/终态记录而无成果证据时显示“结果待补充/证据不足”，不能写“没有进展”。迟到证据补入同一 run 的新摘要修订，保留原记录和补录时间，不新造一次运行，也不改原始起止时间。后续推翻的结论应有更正标记而不是静默删除旧判断。

### 11.3 可检索记录，不静默截断

初始页面可以只展开近期若干条，但必须显示范围、更多记录入口及来源覆盖情况。不能仅把 `rows[-12:]` 改成另一个数字就宣布逐次可查已完成。

运行历史支持按日期/运行选择，并可查看已经记录的较早结果；路线没有变化时，运行成果仍更新。初始展示量是阅读策略，不能成为删除历史或丢弃结果的上限。大量历史按第 8.1 节处理，保持每个打开页面自包含；主界面不能显示实际无法打开的历史选项。

历史缺失和尚未解释的记录分别说明。对于旧版未保存的摘要，只能基于能准确归属的证据补解释并注明补录时间；禁止从当前总体状态倒推每小时“完成了什么”。

### 11.4 问题与成果的可读表达

问题沿用现有正交维度，但主视图翻译为可读句子，例如“阻塞当前验证，Agent 正在排查；若失败需切换路线”，而不是只显示英文枚举。尽量绑定节点或路线；没有足够证据绑定时保留问题并标明关联待确认，不能静默删掉它。

跨项目问题只展示依赖、影响与转交引用，不操作其他项目。已解决问题退出当前阻塞列表，但保留结论和曾造成的路线影响。重要成果不能只写“提交了代码”“完成测试”，应说明其证明对象和对目标的贡献。

主事件时间线突出阶段、策略变化、问题、人工动作、关键验证；逐次运行记录独立保留。前者可以筛选重要事件，不能因此删除后者中的非里程碑运行。

### 11.5 旧图归档合同

优先复用已存在的版本化 semantic history 和索引。必要的新增归档仅在用户级 Observer namespace 中；渲染文件可重建，但作为唯一依据的旧语义版本不能假定可从当前状态重建。归档不移动项目 authority 文档，也不写入 `docs/ai/archive/` 冒充项目事实归档。

每个可查看的图形历史至少保留：target 身份、语义版本/复核身份、当时节点和边、当时状态和问题、来源引用/fingerprint、观察与复核时间、归档时间与原因。布局版本与语义版本分开记录；旧图查看默认保持当时语义，不套用今日节点状态。历史 HTML 可由保存的旧语义重新渲染，但须说明渲染版本；原始已保存历史证据不被改写。

在旧语义被替代或明确失效时，确保旧版可持久访问，再更新当前指针或状态。归档必须幂等：同一版先因 stale 归档、后因 successor 出现，不重复生成同一内容的多份图；可补充关联元数据。普通 heartbeat、重复 snapshot、没有语义变化的刷新不新增路线版本。

归档和索引提交失败不能丢失最后有效版本，也不能让失效旧版继续获得 current 认证。用现有锁、原子写与可重试索引完成最小提交顺序：先确保持久版本内容，再发布索引/当前指针；崩溃留下未索引历史可按身份幂等补齐，不能让索引指向不存在内容。旧版本损坏或来源不全时，显示缺失/不可重建，不从当前图反推补齐。保留政策沿用现有无损历史原则，不把页面性能优化当作删除依据；不另造通用事务框架。

### 11.6 当前优先与用户选择对比

默认展示当前有效图和最近变更摘要；历史页有独立的“历史版本，非当前结论”提示、时间与来源。用户可选择单个归档版本查看，或选择两个同目标、同视图类型的版本对比。

对比重点是：新增/移除/替换的节点、状态变化、关系变化、路线选择、问题影响和关键成果，并给出有依据的变化理由。移除节点不自动等于完成，标题相近不自动等于同一节点。优先按稳定身份对齐，只有有依据的映射才合并。

旧版缺少稳定身份或足够语义时，可以提供诚实的并排版本查看，标明无法可靠自动对齐；不能伪造精确差异。没有记录的历史时期不提供虚假的可选版本。纯布局调整不能被报告为路线改变，跨 target 的两份图不能当作同一路线的前后进度。

## 12. 灵活的数值、进度与趋势展示

### 12.1 启用由适用性和用户意图决定

Q6 已确认纳入本轮。Agent 根据目标、权威指标和现有证据决定是否展示数值、选择什么指标及图型，并保留简短理由。人工可以指定指标、时间范围、baseline 或展示方式，也可以修改/撤销既有选择；不得为了追求固定版式强迫所有任务出现相同图表。

例如有数值优化目标时，可考虑已有 objective/error；有明确组件验收清单时，可显示各项验收状态与可解释数量。以上只是适用性示例，不是对当前 FCC 或其他项目最新成果的断言，也不授权 Observer 发起新的计算。

### 12.2 数据口径

| 内容 | 必须能够解释 |
|---|---|
| 指标身份 | 名称、定义、单位、优化方向或验收含义。 |
| 数值身份 | 当前值、历史最好值、正式验证值或实验候选值；不同身份不混用。 |
| 时间/执行归属 | 测量/计算时点，能确定时关联 run；文件修改时间不自动当测量时间。 |
| 可比条件 | case/数据集、目标函数版本、约束与重要工况等真正影响可比性的条件。 |
| 来源 | 已有证据引用和获取范围；缺失样本、来源冲突、数据陈旧明确表示。 |
| 选择依据 | Agent 的适用性判断或当前有效的人工展示要求，及其生命周期。 |

不同目标函数、数据集、单位或关键条件不能直接连成“持续改善”的曲线。算法/lane 改变应标注；是否需要断线取决于实际指标可比性，而不是仅凭 lane 名相同或不同决定。可比性不明时分组或并列显示，不强行合并。

指标读入采用明确、只读、可审查的来源声明或最小 adapter：限定已授权文件/记录、指标字段、单位、有效值条件和证据定位；不执行来源文本中的表达式或命令，不为补图新跑实验。人工选择指标也不能扩张文件访问范围。

拒绝 `NaN`、无穷、无效数值及来源明确的缺失/失败标记作为有效测量；保留缺项原因，不用零替代。领域哨兵按来源合同处理，不在通用 Observer 中硬编码某个项目的数值。指标重复采集按样本身份去重；测量修订保留依据，候选/正式验证/历史最好值分开展示。

### 12.3 图型和进度表达保持灵活

有一个有效数值时可显示数值与说明，有足够可比样本时才画趋势；适合横向比较时可用简单比较图，不要求一律折线。缺失值不补零；baseline 不成立或分母无意义时，不输出百分比改善。

总体进度优先用有依据的“已完成/正在推进/尚未完成”解释。可以展示可审查的计数，例如明确清单中已验收多少项，但须标明只是该清单口径，不自动等于整体目标完成率。没有明确分母、权重与验收标准，不按节点数、commit 数、测试数生成总进度百分比。

同一轮没有新数值时明确“本轮无新测量”，不能把上轮数值重新当本轮成果。观察到指标更差也应如实保留，不能只取最好点制造单调改善。

### 12.4 人工指定与现有生命周期衔接

人工指定优先于 Agent 自选，但不能覆盖数据真值或制造不存在的指标。指定的数据不存在时，说明缺口和来源；不伪造图表，不自行运行实验补数据。

一次性展示调整、下一次复核请求、长期指标偏好分别复用 transient / one-shot / durable 机制。只改变颜色、密度或在同一已验证序列中筛选范围，可以是纯展示；改变指标含义、数据来源、比较基线或影响路线判断时，应重新审查语义与来源，不能通过纯展示 patch 绕过。

“这次看某指标”不自动变成永久规则；“以后一直显示”才长期保留，并支持替代/撤销。浏览器临时选择只改变查看方式，不能偷偷写持久偏好或项目 authority。

### 12.5 交付边界

优先实现当前真实项目所需的最小数据投影与轻量 SVG 图，不建立通用数据连接器或 BI 平台。Observer 只读取已有证据，不为画图运行 PetroSim、优化、外部 API 采集或新的科学实验。

须覆盖适用、不适用、数据不足、口径变化和人工指定等场景；真实样本能支持时验证至少一条有用指标链路，没有来源时保留真实项目数值验收的缺项说明，而不是填示例数据冒充。

## 13. 持续更新与交互需求生命周期

### 13.1 每次正式观测处理什么

正式 Observer 仍按独立任务运行，按需恢复显式目标身份及必要 authority。每次观测应检查新增/变化的运行结果、目标完整性、计划/路线变化、问题影响、指标数据和有效展示要求；fingerprint 是低成本筛查，不替代对重要变化的阅读。

若路线没有变化，但某轮有新成果，**更新该轮记录和进展解释，路线可以保持不变**。不要求每小时重建地图，也不能因地图 unchanged 就跳过逐次成果整理。run identity、语义版本、观察 revision 和页面生成次数不能互相计数。

### 13.2 Map Review 与归档

遇到路线/策略改变、关键证据影响计划、问题改变路线、并行路径或验收条件变化时，读取必要 authority，记录 review decision、理由、证据和来源 fingerprint，按第 11 节保存旧版及版本关联，再应用新语义、生成当前页。

如果只需要补充运行成果或展示内容，按实际影响选择最小更新范围，不能伪造路线改变。声明 unchanged 也要有理由，但不因此为每次运行强行新增语义版本；同一 target 的语义必须与对应数据快照相容。

### 13.3 三类用户展示需求

沿用既有临时纯展示 patch、下一轮消费的一次性 review request、长期有效的 presentation rule。用户对地图、历史、运行记录或数值展示的要求进入合适的生命周期，而非再增加一套“HTML 专属指令系统”。

改变节点顺序、依赖、完成状态、路线含义、指标口径或比较结论属于语义风险，不能伪装成样式调整。一次性需求成功消费后退出 active context；临时 patch 按既有语义更新规则失效；长期规则可替代或撤销。

纯展示重渲染基于同一 canonical snapshot，不追加 snapshot/run，不刷新事实时间。新运行或新指标证据进入页面须走正式观测/复核，而不是将新事实偷渡进旧 snapshot。

### 13.4 不掩盖生产 Observer 的失效

Production、Maintenance verification、migration 的身份明确分离。维护者先保存故障前证据，再按允许场景验证新渲染器；不能靠人工连续刷新让 Production 看起来没有漏跑。生成漂亮的测试页不等于正式 Observer 已按新规则整理每轮成果或完成归档。

## 15. 执行顺序与阶段交付

阶段是进度与验收单位，不是新的 Workstream，也不是每完成一步就停止、再等下一小时。Q1—Q6 已确认，H0 不需要重复发问。

| 阶段 | 实际工作 | 可审阅交付 | 阶段通过条件 |
|---|---|---|---|
| H0 需求与基线对齐 | 读取本 v1.1；增量核对已有实现、合法 Writer 与 scope；正式落盘唯一计划和指针；检查运行/历史/指标来源。 | 需求—验收映射、精确改动范围、已实现/待实现差距。 | 不重复已完成修复；未将技术候选误当已有 API。 |
| H1 尽早交付真实图 | 用代表性目标接通节点、边、层级、当前位置、问题；同时呈现进度摘要和已有最新运行成果。 | 真正生成的 HTML、浏览器截图、来源与图形测试。 | 边确实渲染，能看出实际进度；不是静态美术稿或卡片伪图。 |
| H2 人类阅读与逐次成果闭环 | 完善中文层级、独立架构、节点联动、每次结果与筛选；完成旧图归档/查看/对比、灵活指标的最小可用链路。 | 当前页、逐次历史、旧版/对比、适用/不适用指标和 stale 等页面。 | Q1—Q6 都有可执行验证入口；不能靠占位按钮宣称完成。 |
| H3 目标完整性与兼容 | expected-target 检查/恢复、撤销、旧数据、异常保存、目标隔离和有条件 Project Overview。 | 空/缺失/损坏/恢复回归及旧数据迁移验证。 | 无假健康、误注册、误复活、半写入或历史破坏。 |
| H4 真实项目整体验证 | ACF + FCC 必测；合法可访问时加入 AStockT_AI；逐次结果对账、路线/架构核对、归档对比和指标口径审阅。 | 实际脱敏页面、浏览器证据、失败→修复记录、来源覆盖和剩余缺口。 | 图形正确、语义正确、每轮结果可查；生产与维护证据不混淆。 |
| H5 发布、安装与独立观察 | 走现有稳定发布流程，安装态回归；正式 Observer 独立更新、归档、逐次成果与指标 dogfood；安全交接。 | 正式版本和真实安装来源、生产页面证据、已完成/剩余事项。 | 新能力已进入实际生成链路；生产验收按最新 authority，如有缺项如实 open。 |

H2 内按可验证的小切片推进：逐次记录与来源 → 归档/当前分离 → 版本查看/对比 → 适用指标；可与 H3 无冲突工作交错。不能因历史/指标尚在完善就迟迟不给用户看 H1，也不能在 H1 后把其余已确认要求无期限降为“可选”。

每个自然 checkpoint 保存真实进度、证据与下一步并继续安全增量工作，不设置固定工作时长/轮数。版本号按正式发布时 authority 确定，不预定为 `.89`，不重发 `.88`；外部授权或真实冲突仅阻塞相应动作，不制造无关空转。

### 15.1 执行焦点与局部阻塞处理

首先做一个真实目标的端到端切片：复用已有已验证 narrative/运行证据 → 实际边和当前位置 → 中文进展摘要 → 真实 HTML/浏览器验收；不能把历史对比、指标 adapter、全项目迁移和全部图型的完善设为这张第一张可用图的前置条件。随后在同一 WS012 内继续 H2/H3/H4，不因 H1 通过就长期停下。

每个 checkpoint 只回写当前可核验结果、失败/缺项和最值得做的下一步。无需每轮重读全文；先读该计划的执行阶段、尚未通过的需求映射与当轮变更相关章节。一次产品检查不需要重复确认用户 Q1—Q6。

浏览器或某个外部项目暂不可用时，对应验收保持 open，继续无冲突的数据/渲染/回归/可访问样例工作；没有实际视觉证据不得关视觉 Gate。一般 issue 进入后续队列；只有新出现且直接阻断本路线的真实安全/运行缺陷才做窄修复，不把旧 continuation P0 或完整发布流程重新变成探索主线。

## 16. 测试与验收矩阵

| 场景 | 通过条件 | 不能接受的替代物 |
|---|---|---|
| 整体进展与普通路线 | 目标、已完成部分、剩余阶段、当前位置和下一步可解释。 | 只有漂亮地图，没有进展与成果。 |
| 分层及展开 | 默认主线完整，细步骤/跨层端点可追溯，状态不因展开而改变。 | 删除未完成阶段换取简洁。 |
| 路线/架构分开 | 两种视图语义明确，可在有来源时联动。 | 一个无图例的混合箭头图。 |
| 分支/依赖/并行 | 边端点与含义正确，分支条件或并行关系可读。 | 卡片排序或强行单线。 |
| 长中文/较大图 | 主要文字可读，无严重遮挡，能定位当前节点。 | 缩成无法阅读的全图轮廓。 |
| 多个当前位置 | 按证据显示，不强制只选一个。 | 忽略并行执行线。 |
| 连续多轮结果 | 每轮独立成果可查，节点关联正确；超过默认展示量仍有可用入口。 | 只保留最后一次/最后十二次可见记录。 |
| 地图 unchanged 但运行有新结果 | 逐次记录更新，地图可保持不变，不丢成果。 | 未重建地图就不整理运行结果。 |
| 同一轮被多次观测 | 只更新对应记录，保留补充证据，不重复计数。 | snapshot/render/generation 次数等于运行次数。 |
| 跨小时、恢复、多执行片段 | 身份有依据，未知映射明确，不按整点切出假运行。 | 固定每小时必须有一个成功结果。 |
| 无成果/失败/授权等待 | 如实说明原因和已知结果，不凑正向进展。 | 所有轮次都写“正常推进”。 |
| 缺记录与不完整结束 | 不伪造起止或时长；缺记录不等于未触发。 | 用 stale timeout 补结束时间。 |
| 数据新但语义旧 | 当前区标待复核，旧图归档可查，不以旧图顶替当前。 | 旧图加灰仍当主图或只改 mtime。 |
| 旧图被新图替代 | 旧语义持久保留，归档/索引幂等，新旧可选择。 | 覆盖旧图后宣称“有历史”。 |
| 历史查看和对比 | 保持旧状态，差异基于稳定身份；身份不足明确退化。 | 用今日状态涂旧图、移除即完成。 |
| 历史不足/损坏 | 有明确缺项提示，保留原证据，不造版本。 | 从今天路线倒推过去。 |
| 归档/索引写失败 | 最后有效版本不丢，不错误宣布迁移成功。 | 半写入后继续更新 current 指针。 |
| 问题改变路线 | 关联位置、处理者、计划影响和 Map Review 同步。 | 页面底部孤立问题列表。 |
| 无配置/缺预期目标 | 如实展示观测范围问题和恢复方向。 | “0 个目标，整体健康”。 |
| 主动撤销目标 | 后续不复活，冲突明确。 | 恢复配置覆盖用户意图。 |
| 旧 schema/缺字段 | 诚实退化或非破坏性迁移，unknown 不等于 done。 | 静默丢字段/历史。 |
| 目标隔离 | A 的路线、运行、历史和指标不串入 B。 | 全项目统一数据覆盖归属。 |
| 适用/不适用/单点指标 | Agent 按证据选呈现方式，无空图凑数，来源明确。 | 所有任务固定折线模板。 |
| 人工指定、修改、撤销指标 | 对应生命周期生效，不复活旧要求；不存在的数据明确缺失。 | 配置永久残留或伪造指定指标。 |
| 指标口径变化与非改善 | 断点/分组/标注正确，坏结果不被删，前后值属于同口径。 | 拼接不同 objective/case 制造下降。 |
| 进度数字 | 分母、权重、验收口径明确；否则采用定性进度。 | commit/节点数直接变总完成率。 |
| 纯展示变更 | 同 snapshot 重渲染，不新增运行/观测、不改事实时间。 | 操作筛选器就产生进展事件。 |
| 离线/file:// | 主图、正文、目标与历史基本导航可用，无外部依赖。 | 在线可用、本地空白或历史 fetch 失败。 |
| JS/渲染失败 | 关键内容可读或诚实退化，last-good 原样保存且错误可查。 | 空白但报成功、旧文件改新时间。 |
| 转义和敏感内容 | HTML/SVG/JSON、指标标签、历史索引均安全，不执行不可信输入。 | 只测试普通 ASCII 文本。 |
| 稳定重渲染 | 相同输入及渲染版本输出稳定，布局不随机跳动。 | 每次刷新换位，妨碍比较。 |
| 独立生产验收 | 真实 Production Observer 身份与结果，不混 Maintenance 样例。 | 手动刷新后声称定时任务正常。 |
| 来源变化与版本解耦 | 多轮成果变化仍逐条记录，fresh-source unchanged 审计不制造重复路线；真正语义变化触发复核。 | 无条件清除 stale、忽略重要变化或每个 heartbeat 归档一版。 |
| 归档失败与只读边界 | 原始版本保留、旧语义不认证 current；只读 status 不写文件。 | 为保留 last-good 继续宣称有效，或只读查询写归档。 |
| 迟到/推翻的成果 | 补同一 run 的摘要修订，分清程序成功、证据完整性和目标验收。 | 缺摘要就写无进展，补录算新 run，改写旧起止时间。 |
| 跨页离线历史比较 | 每个可选版本确实能查看；声明支持的两版在真实 file:// 下能够比较。 | 历史入口存在但跨文件选择无效。 |
| 局部失败 | 一个 target/指标/历史失败不会隐藏无关已验证内容；错误定位明确。 | 整页空白、所有任务都变红或静默吞错。 |
| 非有限值和重复样本 | 依来源合同剔除无效测量并标明缺项，样本去重，修订可追溯。 | NaN/哨兵入曲线，缺失补零，重复点算新成果。 |

机械测试、源数据对账和视觉检查分别记录。DOM/解析断言须检查端点、连线、关系、选中版本与记录身份，不只看 `<svg>` 或标题出现。截图来自真正生成的 HTML，不使用生成式示意图替代产品证据。

逐次结果至少对照能核验的运行样本逐条检查归属和成果；历史测试涵盖新建→失效归档→新图替代→选择旧版/对比；指标测试涵盖 Agent 自选与人工指定。长历史、乱码、empty/stale/failed 等负面状态不能只靠正常截图推断通过。

浏览器检查用执行时可用且获准的工具；工具不可用时该验收保持 open，但继续其他安全有价值工作，不以此伪造视觉 PASS 或扩张权限。

## 18. 人类验收问题与关闭标准

### 18.1 页面本身应能回答的问题

- 最终目标是什么，已经完成哪些部分，现在到哪里，还差什么？
- 为什么现在做这一步，哪些关系是依赖、分支或并行，架构视图又表达什么？
- 选择任意一条有记录的实际运行：本轮做了什么、得到什么、有没有推进阶段/指标/问题，有无完整结束证据？
- 路线不变时，能否仍看到各轮不同的结果；结果不足或没有运行记录时，是否如实说明？
- 当前问题影响哪里，谁处理，是否需要人工动作？
- 当前图依据何时的事实，解释失效后是否退出当前主图，旧图在哪里查看？
- 能否选择已保存的历史版本或两版对比，并看清改了什么及已知原因？
- 适用的指标是否有数值/趋势，口径是什么；人工指定的展示是否生效？
- 是否缺少本该观察的目标，页面有没有把观测缺口误说成健康或项目失败？

### 18.3 Gate 关闭条件

同时满足：需求映射完整、必要回归通过、真实浏览器页面检查通过、语义和 authority 一致、逐次结果可追溯、旧图有真实归档/查看/对比、数值能力符合适用性、异常诚实可见、修复进入通用生成器及正式安装/生产链路。

测试通过不等于视觉通过；维护验证成功不等于独立 Production 验收成功。真实外部历史本来缺失的区段可以明确不可重建，但不能把“历史缺失”当作不实现后续归档和查看的理由。某目标不适合指标可不画，不能因此取消数值展示能力。

执行 Agent 可以依据明确 rubric 检查实际页面并继续迭代，不要求用户每小时人工批准配色或每个 checkpoint。用户新的截图/反馈可以重新打开对应可用性问题；不因此推翻已验证的无关阶段或重跑全部旧发布过程。

本次 Gate 关闭不代表 WS012 长期 maintenance mission 完成，不自动暂停或完成定时任务。
